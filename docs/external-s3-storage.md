# Внешнее S3: подготовка и подключение

22 сентября 2026. Код и конфигурация подготовлены; живой бакет Timeweb ещё не
подключён. Этот документ не подтверждает переключение сервера или работу
Timeweb с нашими реальными ключами. Соседние задачи Telegram/ChatModule не меняются.

## Что меняется

Production уже использует S3 API: меняем адрес и учётные данные хранилища.
Изображения, видео, аудио, вложения чата и payload файловых заданий остаются
под управлением существующих сервисов. PostgreSQL сохраняет метаданные, владельца,
Workspace, документ и ключ объекта. На VPS остаются приложение, БД и временные
файлы обработки. S3 не заменяет RAM и рабочий диск для монтажа/конвертации.

Новый `compose.storage-s3.yaml` отключает запуск локальных MinIO/init по умолчанию
и их зависимости у web/workers. Все получают одинаковые bucket/endpoint/region;
вложения ChatModule также используют внешний адрес вместо `minio.localhost`.
Сети PostgreSQL, Caddy и provider-egress сохраняются. Без этого overlay прежний
MinIO-режим продолжает работать. Локальный `compose.yaml` не изменён.

## Что подготовить в Timeweb

1. Приватный основной бакет в выбранном регионе. Endpoint и region взять из
   настроек именно этого бакета; в endpoint не добавлять имя бакета.
2. Отдельного пользователя для приложения с доступом к основному бакету:
   список/метаданные/чтение/запись/удаление объектов. CopyObject используется при
   финализации проверенного вложения (чтение источника + запись результата).
   Административный аккаунт Timeweb приложению не нужен.
3. CORS под реальный origin приложения. Шаблон:
   [`deploy/storage/cors.example.json`](../deploy/storage/cors.example.json).
   Добавлять localhost только для специально разрешённой тестовой среды.
   Применить через панель или AWS CLI с защищённым credential profile, без
   передачи ключей в аргументах. CORS не делает бакет публичным.
4. Для резервных копий: второй приватный бакет на том же endpoint и отдельный
   operations-ключ, читающий исходный бакет и записывающий backup-бакет.
   Эти credentials передаются только одноразовой операции backup, не приложению.

Документация провайдера: [CORS](https://timeweb.cloud/docs/s3-storage/supported-features/cors-setup),
[дополнительные пользователи](https://timeweb.cloud/docs/s3-storage/manage-storage/additional-users),
[временные ссылки](https://timeweb.cloud/docs/s3-storage/supported-features/presigned-url).

## Конфигурация и предварительная проверка

Значения из [`.env.storage-s3.example`](../.env.storage-s3.example) внести в
защищённый серверный env (доступ 600). Это пример, его placeholders не рабочие.
Заполненный файл не коммитить, ключи не пересылать в чат и не печатать через
`docker compose config`. Не менять S3-настройки работающего приложения до проверки.

Для проверки нового режима использовать отдельный защищённый candidate env,
сохраняющий остальные текущие настройки приложения. Выпущенный образ должен
уже содержать scripts из этой доработки. Compose-файлы добавляются в таком порядке:

```bash
# После cd в каталог релиза; путь к candidate env задаётся локально на сервере.
compose_s3=(docker compose --env-file "$candidate_env"
  -f compose.production.yaml -f compose.timeweb.yaml -f compose.egress.yaml
  -f compose.storage-s3.yaml)
"${compose_s3[@]}" config --quiet
"${compose_s3[@]}" --profile storage-ops run --rm --no-deps storage-probe
```

Это bash-массив, не команда для shell `sh`. Нужен Docker Compose 2.24.4+:
overlay использует [`!override`](https://docs.docker.com/reference/compose-file/merge/)
для замены зависимостей. `run --no-deps` не пересоздаёт web/БД/workers.

Probe создаёт несколько маленьких файлов под уникальным `_ops/s3-probe/...`,
проверяет приватность, чтение диапазона байтов, presigned upload/read, checksum и
финализацию вложения через установленный S3 adapter ChatModule, модельную read-ссылку
и CORS preflight. Затем удаляет свои файлы. Генерацию и платные вызовы AI не запускает.
Если включено версионирование S3, обычное удаление оставит непубличные старые версии
тестовых файлов; их удаляют по точному test-prefix/правилу retention.
Probe не заменяет финальную проверку upload из браузера и доступа AI-провайдера.
Логи не содержат ключей и подписанных URL. При сбое сохраняется код ошибки без тела.

## Переключение сервера

После успешного probe и готовности пакетов:

1. Убедиться, что нет работающих генераций/экспортов; на время переключения
   остановить приём новых записей и workers.
2. Снять согласованный backup БД и текущих файлов. Пользователь разрешил новый
   тестовый сервер с пустой БД; это не разрешение очистить локальную разработку.
3. Если используем старые данные, скопировать объекты с сохранением ключей и
   проверить содержимое. В БД хранится имя bucket, поэтому одной замены endpoint
   при новом имени bucket недостаточно: нужна отдельная проверенная миграция ссылок.
   При чистом развёртывании создаётся актуальная схема БД и пустой основной бакет.
4. Применить candidate env и полный набор overlay к web/worker/pipeline-worker
   через согласованный release-процесс. Профиль `local-object-storage` не включать.
   Overlay не останавливает уже работающий MinIO автоматически; старый контейнер
   отключить отдельно после проверки. Volumes не удалять через `down -v`.
5. Проверить ready/worker/pipeline-worker, загрузку и повторное открытие изображения,
   HEIC, видео с перемоткой/Range, аудио, документа и вложения ассистента.
   Проверить доступ другого Workspace, модельное чтение reference и результат job.
6. Переключить backup timer на новый режим и выполнить тест восстановления.

Старый `deploy/server/reverie-ci-deploy` рассчитан на прежний стек
`/opt/image-prodaction`, его нельзя слепо запускать как сценарий нового Timeweb-релиза.
Окончательное переключение выполняется в задаче деплоя с актуальными env/сетями.

## Резервные копии без скачивания медиа на VPS

```bash
# Только при остановленных writer-процессах для согласованной копии БД и файлов.
"${compose_s3[@]}" --profile storage-ops run --rm --no-deps storage-backup
```

`scripts/s3-backup.mjs` делает серверные CopyObject в уникальный snapshot-prefix
отдельного backup-бакета. Исходные объекты не меняет. Использует ETag precondition:
изменившийся при копировании объект приводит к ошибке, а не тихой порче копии.
Результат печатает небольшой JSON-манифест; сохранить его рядом с соответствующим
dump БД. Имена объектов находятся в приватных `pages/N.json` внутри snapshot.
Только наличие финального `manifest.json` означает законченную копию.
Незавершённый запуск не считается backup и не удаляет предшествующие копии.

В этом срезе CopyObject поддерживает объекты до 5 GiB: более крупный объект
останавливает snapshot с ошибкой. Для таких файлов потребуется multipart-copy.
Snapshot не транзакционный: консистентный dump БД и медиа требует паузы writers.
По одному объекту на запрос, страницы по 500 записей; содержимое медиа не идёт
через диск VPS. Полные snapshots занимают дополнительное место в S3. Retention
для backup-бакета необходимо согласовать/применить до регулярного запуска;
скрипт сам старые копии не удаляет. Это не off-provider disaster recovery.

Для восстановления выбрать snapshot с manifest, пройти `pages/1.json..N.json`,
скопировать каждый `backupKey` обратно в `key` пустого основного бакета,
проверить размеры/контрольное содержимое и восстановить соответствующий dump БД.
Имя целевого основного bucket должно совпасть с БД либо пройти отдельную миграцию.
Никогда не восстанавливать поверх работающего приложения без остановки writers.

На сервере сейчас используется `/opt/reverie-ops/backup.py`, копирующий локальный
MinIO volume. Этот timer пока НЕ изменён. При cutover его медиа-шаг нужно заменить
на `storage-backup`, сохранив текущие dump Production/Identity и защищённые конфиги.
До этого существующие ежедневные копии продолжают работать для текущего MinIO.
У legacy `deploy/server/reverie-backup` добавлен явный отказ для внешнего endpoint,
чтобы он не сообщал об успешной S3-копии, архивируя старый локальный каталог.

## Проверки этого среза

```bash
node scripts/check-production-network-config.mjs
node --test scripts/s3-storage-ops.test.mjs
# Только существующий локальный MinIO; S3 env берётся из локальной конфигурации.
node scripts/s3-storage-local-smoke.mjs --local-only
```

Локальный integration smoke создаёт два уникальных тестовых бакета, проверяет
adapter вложений, делает snapshot, восстанавливает файл и сравнивает байты.
Затем удаляет только собственные бакеты. Скрипт откажется работать на внешнем host.
CI проверяет обе Compose-конфигурации и unit-тесты backup/конфигурации; реальный
Timeweb smoke намеренно выполняется отдельно с защищёнными credentials.

Фактическая локальная проверка 22 сентября: обе Compose-конфигурации, 6 новых
тестов S3 ops и 32 существующих теста assets/attachments/generation payload прошли.
Integration smoke с записью, snapshot и восстановлением байтов прошёл; тестовые
бакеты удалены. TypeScript, ESLint, границы архитектуры и лимиты размеров файлов
прошли. Docker-образы не собирались, работающие контейнеры не пересоздавались.

Отдельно остаются: лимиты объёма Workspace, учёт storage usage, политика удаления
пользовательских файлов, независимые backups и lifecycle временных объектов.
Нельзя включать общее автоудаление `workspaces/*` или payload заданий: они могут
понадобиться для документов и восстановления выполнения после перезапуска.
