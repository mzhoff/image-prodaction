# Тарифы и пополнения Production

21 сентября 2026. Решения владельца + локальный интерфейс; не запуск платных подписок.

## Согласованная модель

| Возможность | Start | Creator | Studio |
| --- | --- | --- | --- |
| Создание материалов и Flows | Да | Да | Да |
| Публикация рецепта в Community | Да | Да | Да |
| Использование рецептов Community | Да | Да | Да |
| Экспорт Flow для переиспользования | — | Да | Да |
| Исполняемые Flows в своих продуктах и сервисах, API | — | — | Да |

Community — будущая публичная поверхность: публикация рецепта не становится
платной привилегией. В интерфейсе она отмечена как развивающаяся возможность.
Предлагаемое правило: запуск чужого рецепта использует бюджет запускающего Workspace,
никогда скрыто не расходует ключ автора. Публичный запуск требует отдельной реализации
с разрешениями, immutable version и изоляцией assets. Публикация не раскрывает ключи,
закрытые материалы и секреты подключений.

Тариф и AI-бюджет — разные сущности. Пакеты пополнения: **$10 / $25 / $50 / $100**,
доступны независимо от выбранной карточки тарифа. Это доллары бюджета генераций,
не фиксированное количество токенов и не цена месячной подписки.
Месячные/годовые цены, скидка за год, storage/seats/concurrency-квоты пока не утверждены.
В бете плата за тариф отсутствует; автоматические списания не включены.

Ни выбор карточки, ни наличие денег не назначают роль владельца/администратора.
Фактические entitlements остаются обязанностью платформенного сервера. Этот срез
не блокирует существующий экспорт и API новыми тарифными ограничениями: сначала
нужен канонический серверный договор доступа, затем проверки каждой операции.

## Общая шторка

Источник заготовки: REVERIE app,
`apps/prototype-web/src/pages/profile-settings/ui/BillingTab.tsx`.
В ней найдены блок подписки и вложенный блок оплаты. Структура адаптирована в
`src/features/subscriptions`; демонстрационные карта/срок списания и локальный
переключатель `subscriptionStatus=active` не перенесены.

Единый `SubscriptionProvider` установлен в root layout. `useSubscriptions()`
открывает native modal dialog в top layer, через portal вне `#app-root`.
Он перекрывает всю рабочую область, в том числе настройки и редакторы, сохраняет
подлежащий документ/чат, закрывается по Escape/крестику и возвращает фокус.
События клавиатуры не должны закрывать лежащие под ним модальные настройки.
Включены полупрозрачная заливка, blur 30px, карточки без внешних обводок,
адаптация узкого экрана и reduced motion.

Точки входа: меню аккаунта, настройки «AI и баланс», Usage, баланс Canvas,
CTA общего `AiAccessDialog` и `AiAccessBanner`. Ошибки персонального лимита
участника сохраняют обращение к владельцу вместо предложения новой покупки.
Текст/материалы не отправляются в AI при подтверждённом отказе доступа.

Шторка отражается в URL текущего экрана: `?billing=budget` сразу открывает
пополнение, `?billing=plans` — тарифы. `billingWorkspace` сохраняет выбранное
пространство; это только UI-селектор, права повторно проверяются на сервере.
Все CTA пополнения ведут на `budget`, эта же вкладка используется по умолчанию.
Открытие добавляет запись истории; смена вкладки/пространства обновляет её без
перезагрузки документа. Назад закрывает шторку, Вперёд открывает её снова.
Прямая ссылка и перезагрузка восстанавливают вкладку. Закрытие прямой ссылки
убирает только параметры шторки, сохраняя адрес документа, фильтры и чат.

Workspace берётся из места открытия; сервер `/api/workspaces` возвращает
доступные пространства и роль. Если исходный ID недоступен, другое пространство
не подставляется автоматически. Пополнение в UI доступно владельцу. Identity
повторно проверяет владельца при приёме квитанции/начислении.

## Публичная настройка перевода

`REVERIE_BILLING_PUBLIC_CONFIG_FILE` указывает на JSON-файл с публичной информацией.
В development без переменной читается игнорируемый Git файл
`src/app/config/billing.local.json` — он доступен и в текущем Docker source mount.
В production автоматического выбора тестового бота нет.

```json
{
  "telegramBotUsername": "reverie_local_test_bot",
  "transfer": null
}
```

Для включения реквизитов `transfer` должен содержать все поля:
`recipient`, `bank`, `details`, `purpose` (строки) и `rubPerUsd` (положительное число,
не более двух знаков после запятой). Курс и реквизиты утверждает владелец.
Неполная/ошибочная конфигурация оставляет состояние «Условия оплаты уточняются».
Сумма в рублях считается через целые копейки; выбранный долларовый бюджет показан
отдельно. Конфигурация целиком публична: секреты ЮKassa, бота и OpenRouter сюда
никогда не помещать. В браузер передаются только перечисленные разрешённые поля.
После изменения файла обновить страницу; для опубликованного контура проверить
обновление серверной конфигурации при очередной доставке.

## Ручной пилот

1. Владелец выбирает Workspace и сумму бюджета на сайте.
2. На сайте читает согласованную сумму в рублях и реквизиты ИП.
3. Совершает банковский перевод вне Telegram; сохраняет банковскую квитанцию.
4. Нажимает «Открыть в Telegram». Production проверяет сессию и владельца, затем
   подписанным серверным запросом передаёт Identity выбранные Workspace, тариф и USD.
   Identity сохраняет заявку и ставит сообщение с инструкцией в очередь бота.
   Бот не ждёт от пользователя повторного ввода суммы и названия пространства.
   Если Telegram впервые открывает переписку, может потребоваться кнопка «Старт».
5. Пользователь отправляет PDF/JPG или фото квитанции в эту переписку.
   `budgets/receipts.ts` повторно проверяет владельца и связывает её с заявкой.
   Если заявки с сайта нет, прежний сценарий с выбором Workspace сохраняется.
6. Identity копирует исходную квитанцию администратору вместе с Workspace и
   предложенной суммой. Оператор проверяет реальное поступление, нажимает кнопку
   с суммой, затем подтверждает начисление. Другую сумму можно задать через `/credit`.
7. Существующий журнал и worker создают/обновляют `WSP_{workspace_id}` и подключение.
   После серверного подтверждения бот уведомляет пользователя, «Проверить доступ»
   обновляет общий frontend cache. Выбор пакета сам по себе денег не начисляет.

Заявка с сайта не является платежом или назначением тарифа. Квитанцию загружает
сам пользователь. Повторные клики возвращают ту же активную заявку; другой выбор
требует завершить или отменить её в боте. Срок заявки — 24 часа. Ссылка связана с
ботом и Telegram-пользователем, а подпись серверного запроса — с телом и временем.
Событие промежуточной кнопки `View in Telegram` на сайте Telegram нам недоступно:
сообщение ставится в очередь нажатием нашей кнопки, `/start` повторно открывает контекст.
Реальная банковская операция, доставка PDF/JPG и выпуск ключа не выполнялись при проверке.
Приём через браузер с ботом поддержки не является заявлением о гарантированном
соответствии любому сценарию Telegram: не добавлять в бот банковские реквизиты,
сторонние digital invoices или обход Stars.

## ЮKassa: что готовим для ИП

Проверено по официальным источникам 21.09.2026.

- Зарегистрировать кабинет как ИП, заполнить адрес, реквизиты и контакты,
  загрузить паспорт ИП и подписать договор. Дополнительные документы зависят от
  деятельности/представителя. Указанный сервисом обычный срок — три рабочих дня,
  без гарантии срока для нашей заявки. [Документы ЮKassa](https://yookassa.ru/docs/support/payments/onboarding/docs).
- Подготовить доступный сайт с реальным описанием Production и продаваемых услуг,
  настоящими ценами, способом получения доступа после оплаты, офертой,
  контактами и реквизитами ИП. Не подавать демонстрационные тарифы как действующую
  продажу. [Требования к сайту](https://yookassa.ru/docs/support/payments/onboarding/arrangement).
- До заявки согласовать наименование услуги: доступ к ПО и/или аванс за AI-операции,
  порядок расходования, возврата, срок действия бюджета и цену в рублях.
  Юридическую формулировку, налоговый режим/НДС и момент зачёта аванса уточнить
  с бухгалтером и ЮKassa; «продажа долларов OpenRouter» не является готовой моделью договора.
- Определить фискализацию. Для большинства ИП нужна онлайн-касса либо подходящее
  решение отправки чеков; ИП на НПД — отдельный режим. Банковская квитанция
  не заменяет фискальный чек. [Чеки и 54-ФЗ](https://yookassa.ru/developers/payment-acceptance/receipts/basics).
- Для первых переводов тоже нужна проверка правил кассы. Тёплый контакт и ручное
  подтверждение не создают отдельного освобождения. Реквизиты готовим для
  расчётного счёта ИП, а не личной карты. [Позиция ФНС о переводах на личные счета](https://www.nalog.gov.ru/rn25/news/activities_fts/16642984/).
- Тестовый магазин можно открыть до договора; настоящие платежи включаются после
  подключения. [Процесс подключения](https://yookassa.ru/docs/support/payments/onboarding/overview).

### Требования к будущему платёжному механизму

В платформенном Identity/budget модуле: `payment_intent` с владельцем, Workspace,
версией предложения, рублёвой суммой в копейках и долларовым бюджетом; отдельно
состояния оплаты, фискального чека и подключения ключа. Запрос оплаты проверяет
владельца на сервере. Клиентская сумма и выбранный план не являются доказательством.

Создание платежа с сохранённым `Idempotence-Key`; API shopId/secret только на сервере.
После webhook перечитать платёж через ЮKassa, сверить магазин, окружение test/live,
валюту, сумму, metadata и `succeeded`, затем ровно один раз записать credit и outbox.
Return URL браузера никогда не подтверждает оплату. Провайдер защищает повторения
24 часа; наш ledger хранит уникальность payment ID постоянно. Отдельно обработать
отмены, возвраты, повторные webhook, уже израсходованный бюджет и сбой выпуска ключа.
[Webhook verification](https://yookassa.ru/developers/using-api/webhooks),
[идемпотентность](https://yookassa.ru/developers/using-api/interaction-format).

Для подготовки заявки осталось получить: налоговый режим и используемую кассу,
реквизиты ИП, утверждённый курс/рублёвые цены, правила возвратов/действия бюджета,
домен для подачи и рабочие контакты. Паспорт и банковские документы владелец
загружает непосредственно в личный кабинет ЮKassa, не в чат разработки.

### Включение передачи в Telegram

Production использует существующие `REVERIE_IDENTITY_ISSUER` и
`PLATFORM_PROJECTION_SECRET`. Identity — действующий budget module и Telegram-бота;
новые секреты не нужны. До перезапуска Identity применить его budget migration:
добавляется таблица `platform_budget.handoff`, существующие ID и балансы сохраняются.
Контракт — `budget.handoff.v1`, endpoint Identity `/v1/platform/budget-handoffs`,
endpoint браузера `/api/billing/telegram`. Прямой доступ браузера к Identity endpoint
не разрешён. Очередь доставляет сообщения с повторами при временном сбое Telegram.


### Своя сумма и вход из Telegram — 22 сентября 2026

Карточка «Своя сумма» раскрывает Slider из PRODaction UI: $10–200, шаг $1.
Выбор суммы и «Продолжить» показывают условия; сами по себе они не создают
платёж, подписку или доступ. Кнопка проверки доступа на этом экране удалена.

Главное меню Telegram содержит «Пополнить баланс». Единственное принадлежащее
пользователю пространство выбирается автоматически; при нескольких существующих
пространствах бот запрашивает выбор. Если первый вход в продукт ещё не завершён,
бот предлагает закончить его. Создание дополнительных пространств не предлагается.
Кнопки $10/$25/$50/$100 и введённое целое число $10–200 создают ту же handoff-заявку,
что сайт. PDF/JPG пользователь отправляет ответным сообщением; администратор
проверяет поступление и подтверждает сумму в существующей цепочке.

Подписанный `/v1/platform/budget-workspaces` дополнительно возвращает `transfer`
из публичного allowlist billing-конфига либо null. Identity сохраняет снимок
инструкций в заявке. Реквизиты не дублируются в настройках бота. При отсутствующих
реквизитах бот явно просит согласовать условия с администратором. Длинные реквизиты
не обрезаются: вместо частичных данных бот даёт ссылку на кабинет.
