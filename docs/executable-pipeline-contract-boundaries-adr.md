# ADR: явные контракты входов и выходов executable pipeline

Статус: согласовано для реализации P0, 2026-08-21.

## Контекст

До этого Studio автоматически считала корневые `Text Prompt` и `Import Image`
входами endpoint, а листья графа — выходами. Такой вывод неоднозначен:

- постоянный системный prompt ошибочно становится изменяемым входом;
- техническая Preview-нода может неявно определять публичный ответ;
- нельзя явно задать optional-поле, default, описание и JSON-схему;
- изменение расположения или связи нод может незаметно изменить публичный
  контракт потребителя.

Image Production должен публиковать неизменяемую версию capability с явным,
проверяемым контрактом. Content Hub, Telegram, мобильные приложения и другие
потребители не должны зависеть от canvas node IDs или формы draft-графа.

## Решение

### 1. Границы графа

В Studio добавляются специальные ноды:

- `Pipeline Input` — объявляет внешние поля запуска и предоставляет
  типизированный output-port для каждого поля;
- `Pipeline Output` — принимает типизированные значения и объявляет публичные
  поля результата;
- `Structured Output` — преобразует текстовый или JSON-контекст в настоящий
  JSON по явно заданной рекурсивной схеме.

Обычная производственная нода не получает скрытый флаг `input` или `output`.
Контекстные действия `Вынести в Pipeline Input` и `Сделать Pipeline Output`
являются только быстрым способом создать или дополнить соответствующую
контрактную ноду.

### 2. Типы P0

Публичные поля P0 поддерживают:

- `text`;
- `number`;
- `boolean`;
- `image`;
- `json`.

`json` может содержать дочерние поля `text`, `number`, `boolean` и вложенные
`json`-объекты. `image` разрешён только как самостоятельное поле верхнего
уровня: артефакт нельзя безопасно сгенерировать или вложить в строгий JSON P0.
Внутренние виды портов `any`, `preset`, `reference`, `subject`,
`location` и `publication` не являются публичным контрактом P0.

Каждое поле имеет стабильный технический `id`, публичный `key`, тип,
обязательность и описание. Optional-поле может иметь default. После публикации
ключ и тип изменяются только в новой immutable версии.

### 3. Structured Output UX

Карточка следует визуальной модели `Text Splitter`: одна строка на поле.
В строке показываются имя, required/optional и тип. Тип меняется через popover.
JSON-строка раскрывается и показывает вложенные поля с отступом. Схема хранится
в данных ноды и компилируется в версионируемый runtime-контракт.

`Structured Output` использует отдельную серверную операцию
`ai.structured.generate`. Она возвращает объект, а не JSON-строку, проверяет
результат по схеме и завершает run ошибкой `pipeline_output_invalid`, если
провайдер не смог сформировать валидный результат.

### 4. Проверки

Публикация блокируется, если:

- нет явной Input- или Output-ноды в новом contract-mode;
- обязательный output не подключён;
- соединены несовместимые типы;
- ключи полей пусты, дублируются или имеют недопустимый формат;
- JSON-схема некорректна;
- исполняемая нода не имеет production-handler;
- присутствует цикл или ссылка на неизвестный порт.

Optional-поле без связи не блокирует публикацию. Runtime проверяет вход до
создания платной задачи и проверяет выход до успешного завершения run.

### 5. Совместимость

Уже опубликованные версии остаются неизменяемыми и продолжают исполняться по
сохранённому compiled plan. Для draft-графов без явных boundary-нод временно
сохраняется legacy-компиляция. Новый contract-mode включается, как только в
секции появляется `Pipeline Input` или `Pipeline Output`; смешивать explicit и
legacy границы в одной публикации нельзя.

Legacy-режим будет удалён только после отдельной миграции сохранённых draft и
проверки активных потребителей.

### 6. Потребители и внешние API

Потребитель endpoint и исходящее соединение — разные сущности:

- `Pipeline Consumer` определяет, кто запускает опубликованную версию и с
  какими rate/concurrency/cost scopes;
- `Connection` хранит server-side credential внешней системы;
- будущая `HTTP Action` выбирает Connection и заранее объявленную operation,
  но не хранит секрет и произвольный URL на canvas.

Content Hub вызывает semantic capability и сам сохраняет свою доменную сущность.
Pipeline анализа темы не пишет напрямую в базу Content Hub.

## Последствия

- публичный контракт становится видимым на canvas и предсказуемым;
- постоянные prompts и references остаются частью immutable реализации;
- Playground и SDK могут строить форму строго по схеме;
- structured JSON можно безопасно передавать разным продуктам;
- добавляется переходный legacy-режим, который необходимо удалить после
  миграции, а не поддерживать бессрочно.
