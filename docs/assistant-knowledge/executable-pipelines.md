# Executable Pipelines в Image Production

## Что такое Executable Pipelines и для чего они нужны

**Executable Pipeline (исполняемый пайплайн)** — опубликованный и пригодный для
серверного запуска рецепт обработки данных. Пользователь визуально собирает граф
из нод в Studio, проверяет его и публикует подготовленную секцию. Опубликованная
версия фиксирует граф, типизированные входы и выходы и доступные серверу операции.

Удобная продуктовая метафора:

- Image Production и каталог `Pipelines` — **книга рецептов**;
- ноды и связи — шаги рецепта и порядок их выполнения;
- опубликованная версия pipeline — конкретная зафиксированная версия рецепта;
- Runtime и `pipeline-worker` — **главный повар**, который исполняет рецепт;
- приложение-потребитель передаёт «ингредиенты» во входах и получает готовый
  результат в типизированных выходах.

Так один проверенный визуальный процесс не нужно заново программировать в каждом
продукте. Его можно вызывать из backend веб-приложения, мобильного сервиса, CMS,
CRM, бота или другого доверенного сервиса. Например, один рецепт может принять
текст, сгенерировать изображение и вернуть ссылку на готовый asset.

## Что уже работает сейчас: публикация и Runtime API

После публикации pipeline получает стабильный `publicId`. Его защищённый endpoint
имеет вид `POST /v1/pipelines/{publicId}/runs`. Стабильный адрес отделён от
неизменяемой версии рецепта: при новой публикации активная версия может
обновиться, а интеграционный `publicId` остаётся прежним. Поэтому стабильный
адрес нельзя путать с навсегда неизменным контрактом: перед активацией новой
версии владелец должен проверить совместимость её входов и выходов с
приложениями-потребителями.

Внешний HTTP Runtime API уже реализован. Доверенный backend-потребитель может:

1. поставить запуск в очередь с `Authorization: Bearer ...` и обязательным
   `Idempotency-Key`;
2. получить `202 Accepted`, идентификатор запуска и `statusUrl`;
3. проверить состояние через `GET /v1/runs/{runId}`;
4. после `succeeded` получить типизированные `outputs` и защищённые ссылки на
   артефакты;
5. отменить незавершённый запуск через `POST /v1/runs/{runId}/cancel`.

Одинаковый `Idempotency-Key` с теми же входами возвращает тот же запуск и защищает
потребителя от случайной двойной генерации и двойных расходов. Playground внутри
Image Production уже использует тот же pipeline runtime как встроенный
потребитель, но авторизуется пользовательской сессией через внутренние маршруты.

Не любой граф уже исполним на сервере. Публикация отклоняется, если в секции есть
нода без production-handler. Текущий registry поддерживает основные текстовые
операции, AI-анализ и AI-генерацию изображений; часть builder-, correction- и
external-publication-нод ещё не входит в production runtime.

## Как вызвать рецепт из другого приложения сегодня

Текущий путь интеграции без SDK выглядит так:

1. Владелец собирает и проверяет секцию графа в Studio.
2. Он публикует её как Executable Pipeline и получает `publicId`/endpoint.
3. Для конкретного pipeline и приложения-потребителя создаётся отдельный service
   token. Сейчас это серверная административная операция, а не публичная форма в
   интерфейсе.
4. Backend приложения хранит token в secret-хранилище и отправляет на endpoint
   входные данные по опубликованному контракту.
5. Backend следит за статусом запуска и передаёт своему интерфейсу готовые outputs
   или безопасную ошибку.

Под «вставить ссылку на pipeline в код приложения» следует понимать использование
стабильного API endpoint или `publicId`, а не URL страницы редактора. Endpoint
доступен извне, но не является анонимным: каждый вызов требует service token.

Token нельзя встраивать в браузерный JavaScript, публичный мобильный bundle,
репозиторий или документацию. Если пользовательское приложение не имеет
доверенного backend, для него нужна отдельная безопасная схема выдачи
краткоживущих ограниченных полномочий; текущий долгоживущий Bearer token для этого
не предназначен.

## Что планируется: SDK для приложений-потребителей

Публичный SDK **ещё не выпущен**. Он должен стать удобной типизированной оболочкой
над уже существующим Runtime API, а не вторым исполнителем и не копией логики
pipeline. Runtime остаётся единственным «главным поваром», а SDK помогает разным
приложениям правильно сделать заказ.

Планируемая зона ответственности SDK:

- безопасно настроить адрес Image Production и серверную авторизацию;
- обратиться к pipeline по стабильному `publicId`/endpoint;
- передать входы по контракту рецепта и сформировать `Idempotency-Key`;
- поставить запуск, дождаться результата или отменить его;
- вернуть типизированные outputs и получить защищённые артефакты;
- унифицировать ошибки, retry, timeout и техническую телеметрию для разных
  продуктов.

Конкретное имя npm-пакета, программный интерфейс SDK и дата релиза пока не
зафиксированы. Нельзя выдавать пример предполагаемого SDK API за уже доступную
библиотеку. До его выпуска интеграция выполняется через подтверждённый HTTP
Runtime API с backend стороны приложения.

## Как ассистент должен объяснять внешний вызов

На вопрос «могу ли я вызвать опубликованный pipeline из своего приложения?»
следует отвечать: **да, уже сейчас через защищённый HTTP Runtime API из доверенного
backend; удобный SDK поверх него находится в планах**. Нужно кратко упомянуть
`publicId`, Bearer service token, `Idempotency-Key` и асинхронное получение
результата.

Нельзя путать два разных сценария:

- внешний сервис **запускает весь pipeline через Runtime API**;
- отдельная нода Export, Telegram или другая publication-нода публикует результат
  как один из шагов графа.

Если пользователь спрашивает о точной схеме входов/выходов конкретного pipeline,
нужно опираться на его опубликованный контракт или Playground. Если этого
контракта нет в доступном контексте, ассистент не должен придумывать поля.
