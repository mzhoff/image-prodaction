# Сессии Image Production и соседних приложений

Текущий локальный статус: **установлено и проверено после перезагрузки macOS
2026-09-06**. Docker восстановлен; прежний блокер запуска ниже оставлен как история.

## Причина частых выходов (2026-09-06)

Image Production и Content Hub использовали стандартное имя Better Auth
`better-auth.session_token`, host-only cookie с `Path=/`. Разные порты на одном
хосте **не разделяют cookies**. Поэтому вход во второе приложение перезаписывал
cookie первого; разные серверные секреты и базы не позволяли принять чужую
сессию. Это воспроизведено на Better Auth 1.6.23 с двумя независимыми адаптерами.
В действующей базе Image Production проверен срок существующих сессий: 168 часов,
а не несколько минут. Значения cookies, токены и персональные данные не выводились.

## Текущая политика

Источник истины: `src/shared/auth/session-policy.ts`, подключённый в реальную
серверную композицию `src/modules/authentication/server/auth-server.ts`.

- Все cookies Better Auth получают префикс `image-production`.
- Сессия хранится в PostgreSQL; cookie содержит подписанный идентификатор сессии,
  не пароль и не ключ интеграции.
- Срок — семь суток. При использовании сессии после истечения суточного интервала
  обновления Better Auth продлевает серверный срок и cookie ещё на семь суток.
  Это скользящий срок, а не обязательный выход каждую неделю при активной работе.
- Форма входа использует `rememberMe: true`.
- Сохраняются `HttpOnly`, `SameSite=Lax`, `Path=/`, host-only область.
  Для HTTPS Better Auth автоматически устанавливает `Secure` и `__Secure-`.
  Незащищённый HTTP разрешён конфигурацией только для локальной разработки.
- Cookie cache выключен: серверная база остаётся источником истины, отозванная
  сессия не продолжает работать из кэша. Проверки Origin/CSRF и rate limit сохранены.
- `freshAge` для чувствительных операций не увеличивается. Долгая сессия не должна
  автоматически означать право выполнять чувствительные действия без перепроверки.

Пересоздание контейнера само по себе не сбрасывает вход: нужны та же база сессий,
стабильный `BETTER_AUTH_SECRET` и тот же браузерный хост. Смена секрета, отзыв,
истечение срока, очистка cookies, завершение приватного окна или смена хоста
могут потребовать повторного входа. `localhost` и `127.0.0.1` — разные хосты;
используйте один привычный адрес, например `http://127.0.0.1:7310`.

## Переход и границы изменения

После установки новой версии потребуется **один повторный вход** в Image
Production. Старую общую cookie не принимаем как запасной вариант и не удаляем:
она может принадлежать Content Hub. Нельзя очищать все cookies хоста при выходе.
Новая версия должна работать, даже если соседний продукт ещё использует старый
префикс. При откате на старую версию потребуется вход со старым форматом cookie,
а конфликт портов вернётся.

Первое исправление меняло только Image Production. По последующему прямому
согласованию 2026-09-06 Content Hub также переведён на префикс `content-hub`,
включая очистку cookies в его admin proxy. Базы, ключи интеграций, grants и
bindings не меняются. Уникальные имена устраняют взаимную коллизию этой пары.
Каждому другому независимому Better Auth приложению
также нужен собственный префикс. Для production предпочтительны отдельные HTTPS
хосты с host-only cookies: имена предотвращают случайную коллизию, но не создают
границу безопасности между недоверенными приложениями на одном хосте.

Общий Identity/SSO в будущем — отдельная согласованная интеграция, не одинаковая
cookie, общий секрет или прямой доступ к базе другого продукта.

## Проверки

- `src/shared/auth/session-policy.test.ts`: воспроизведение старой коллизии;
  независимые вход/выход в обоих направлениях; переход без удаления чужих cookies;
  срок и защитные атрибуты HTTP/HTTPS; пересоздание auth-сервера с прежней БД;
  суточное обновление; отказ истёкшей и отозванной сессии.
- `e2e/auth-cookie-isolation.spec.ts`: реальный Chromium и два локальных HTTP
  сервера на разных портах, вход/выход в обоих направлениях. Изолированные
  тестовые аккаунты существуют только в памяти; базы продуктов не затрагиваются.
- Ручной тест: войти в Image Production и Content Hub в одном браузере на одном
  хосте, поочерёдно обновить обе вкладки, выйти из одного приложения и убедиться,
  что второе остаётся авторизованным. Не требуется удалять cookies всего браузера.
- После локального обновления `web` использовать `compose.integration.yaml` и
  проверить доступ из Content Hub к `image-production-api:3000`, затем Runtime v2
  connection без платной генерации.

## Проверенный локальный статус 2026-09-06

Исправление внесено в исходники. Unit suite: 761 pass, 10 skip, 0 fail;
Chromium cookie-isolation E2E: 1 pass. Typecheck, lint, architecture, file-size и
`git diff --check` прошли. Изменений базы и production deployment нет.

Установка в локальный контейнер **не завершена**: во время Docker build общий
Docker Desktop перестал отвечать. В VM log повторяется
`virtio_net ... NETDEV WATCHDOG ... TX timeout`, Docker API возвращает 500/timeout,
Image Production и Content Hub недоступны с хоста. Это отдельная неисправность
локального окружения; изменённый auth-код ещё не запущен в контейнере.
Клиентские процессы нашей сборки остановлены. Общий Docker и чужие контейнеры
не перезапускались. До сборки было около 32 GiB свободно, после остановки — 31 GiB;
build cache до задачи был пуст, очистка освободила 0 B. Итоговый объём Docker
проверить нельзя до восстановления engine; базы, volumes и образы не удалялись.

Продолжение: согласованный перезапуск Docker Desktop (затронет соседние проекты),
проверка текущих контейнеров/сборок/диска, сборка `web` с private-packages overlay,
запуск только `web` с `compose.yaml` + `compose.integration.yaml`, проверка HTTP
и реального Runtime v2 connection из Content Hub без генерации. Затем один
повторный вход пользователя и ручная проверка двух приложений.

Обновление после согласованного перезапуска Docker: restart остановил старый
Docker, но запуск VM и отдельный повторный start завершились ошибкой
`Invalid virtual machine configuration. The storage device attachment is invalid.`
Docker.raw и desktop.img существуют и доступны для чтения; это не проверка
целостности баз. Контейнеры пока не запущены, API сборка Content Hub и тесты обоих
продуктов готовы. Ничего не удалено, свободно около 32 GiB; активных host build
процессов нет. Следующий шаг — перезагрузка Mac пользователем, затем восстановление
Docker и выполнение оставшихся локальных проверок. Автоматическая перезагрузка
компьютера и Factory Reset не разрешены.
