## Вывод

Image Production можно выпускать самостоятельно вместе с существующим Identity, не дожидаясь выпуска Content Hub. Базовые границы продуктов уже подходят для этого: собственные процессы, продуктовые базы, общий вход через OIDC и отдельный производственный runtime.

Текущий checkout пока нельзя считать готовым релизом. Требуются устранение блокеров CI, проверка production-сборки с Identity, подготовка адресов и окружения, короткий onboarding, выдача управляемого бюджета и приёмка на реальном домене. Полный набор пожеланий — общий Workspace, финансовый кабинет, рефералы, onboarding, несколько продуктов по путям и интерфейсная доработка — не является одной небольшой настройкой.

Выпуск к завтра реалистично рассматривать как ограниченный пилот с личными пространствами и понятными лимитами. Это оценка по коду, а не подтверждение срока или нагрузочной ёмкости.

## 2. Адреса и независимый deployment

Один сервер может обслуживать несколько приложений. Прокси принимает HTTPS-запрос и выбирает приложение по hostname или пути. Общая навигация при этом не требует общей базы или объединения frontend-сборок.

### Что мешает механическому переносу на /production

- В [next.config.ts](/Users/m.pyzhov/WORKSPACEs/Development/PRODaction/image-prodaction/Repos/image-prodaction/next.config.ts:4) нет `basePath`.
- IP использует корневые `/api/...`, `/login`, `/account`, URL ассетов и ресурсов. Например, [asset DTO](/Users/m.pyzhov/WORKSPACEs/Development/PRODaction/image-prodaction/Repos/image-prodaction/src/entities/asset/server/asset-dto.ts:33).
- Identity consumer явно принимает только callback `/api/auth/identity/callback`; внешний `/production/api/auth/identity/callback` сейчас не пройдёт его проверку.
- Identity server разрешает только origin в `IDENTITY_BASE_URL`, а issuer общего клиента должен оканчиваться ровно на `/api/auth`. Размещение всего Identity под `/auth` потребует изменения контракта, UI, cookies и проверок: [config](/Users/m.pyzhov/WORKSPACEs/Development/GIGONOM/Projects/Ludimogut/Repos/apps/identity/src/config.ts:20).
- У IP Caddy направляет весь домен в IP. У Hub свой Caddy, где `/api/*`, `/mcp*`, `/.well-known/*` принадлежат Hub API. Склеить эти два catch-all конфига нельзя.
- Hub уже переводится на `/hub`, но это часть текущего незакоммиченного изменения. Старый `/admin` остаётся только совместимым redirect, не названием пользовательского продукта.

Руководства установленного Next.js подтверждают: `basePath` задаётся во время сборки; он не исправляет произвольные fetch и все URL ресурсов. Переходы между независимыми приложениями выполняются обычной полной навигацией. Проверены локальные guides `basePath.md` и `multi-zones.md`.

### Два варианта

| Вариант | Схема | Оценка |
|---|---|---|
| Минимум изменений для срока | `production.<домен>`, `id.<домен>`, далее `<домен>/hub` и сайт в корне | Использует текущие корневые URL IP и Identity; меньше риск для завтрашнего пилота |
| Продукты строго по путям | `<домен>/production`, `<домен>/hub`, сайт в корне; Identity на `id.<домен>` | Подходит целевой навигации, но сначала нужна адаптация IP под basePath и тесты через прокси |

Если в будущем вообще все адреса, включая Identity, потребуются на одном origin, это третий, более широкий вариант: требуется переработать текущий Identity path/issuer contract. Для нынешнего пилота пользователь разрешил поддомены, поэтому эта работа не нужна.

После уточнения пользователя для дедлайна рекомендован первый вариант. Второй технически возможен, но добавляет работу до выпуска. Имена приведены как предложение, DNS не изменялся. Готовность конкретных production URL не проверялась. Новые зарегистрированные домены не нужны: достаточно DNS-записей id и production внутри имеющегося домена.

Разные пути на одном origin — разделение маршрутов, а не браузерная граница безопасности. Уязвимость скриптов одного такого приложения может затронуть соседнее. У продуктов должны оставаться серверная авторизация, разные имена session cookies и независимые secrets; Identity лучше сохранить на отдельном origin с host-only cookie.

Для схемы по путям нужны:

1. единый контракт внешних URL, включая browser API, auth callback, static assets и media;
2. IP basePath + URL helpers + сохранение совместимости уже записанных asset URL;
3. точные OIDC callback и trusted origins, без wildcard;
4. правила одного внешнего прокси для каждого префикса, без пересечения API;
5. no-store для auth/private ответов, отсутствие code/token/query в access logs;
6. проверка загрузок, скачивания, video Range, streaming чата и длинных AI-запросов;
7. сохранение исходной глубокой ссылки через Identity и onboarding.

## 3. Identity, Workspace и будущий Content Hub

Общий Identity уже связывает человека между продуктами. Однако общий аккаунт и общий Workspace — разные задачи.

IP создаёт personal Workspace со своим UUID. Hub [создаёт собственные Organization/Workspace/membership](/Users/m.pyzhov/WORKSPACEs/Development/GIGONOM/Projects/Ludimogut/Repos/apps/api/src/server/identity-workspace.ts:7), причём фактическое kind сейчас TEAM. Поэтому «вошёл тем же аккаунтом» ещё не означает «попал в то же пространство и бюджет».

Предложение для пилота:

- один личный IP Workspace на участника, с возможностью задать имя в onboarding;
- финансовый владелец определяется через глобальный identity subject, execution остаётся привязан к IP workspaceId;
- не пересоздавать существующие пространства и не менять их IDs;
- зафиксировать короткий ADR о связи global account → product user → product workspace;
- до подключения Hub определить канонический Workspace либо явное серверное сопоставление пространств, права и entitlement. Не выводить это сопоставление из email или имени.

Если один и тот же Workspace во всех продуктах обязателен уже завтра, его минимальный registry/provisioning API становится отдельным блокером выпуска. Текущего SSO для этого недостаточно.

Платформенный аккаунт хранит личность и способы входа. Профиль клиента можно хранить в отдельном account-profile модуле, связанном с subject. Ответы, специфичные для производства, и прогресс IP onboarding остаются в IP. Общие реквизиты не нужно спрашивать заново в Hub.

Общий кабинет может выглядеть как одинаковый view внутри оболочек продуктов; данные при этом поступают через API их владельцев. Не требуется превращать его в отдельный маркетинговый продукт.

Ограничение безопасности: logout/reset в Identity сейчас не отзывает уже выданные сессии продуктов. Для пилота нужен проверенный способ блокировки участника и его расходов в IP; интерфейс не должен обещать глобальный выход, которого нет. Полный межпродуктовый отзыв — отдельная обязательная работа перед расширением доступа.

## 4. Telegram и реферальная связь

Текущий Telegram flow: страница продукта → Identity → открыть бота → сравнить код и подтвердить → вернуться в исходный браузер → продукт. Webhook проверяет secret и private chat, имя Telegram не является идентификатором аккаунта.

Простой `/start` уже создаёт/находит аккаунт, но возвращает инструкцию самостоятельно открыть продукт. Для аудитории марафона нужны понятные кнопки «Открыть Image Production» и обработка открытия из мобильного Telegram. Не заменять browser-bound challenge ссылкой с постоянным токеном.

Бот должен иметь одного владельца webhook. Можно выбрать платформенного бота либо заранее определённый общий ingress; нельзя при настройке Identity перезаписать webhook используемого Content Hub бота. Реальная доставка Telegram в этой задаче не проверялась.

Минимальный referral-модуль — отдельная ответственность рядом с Identity:

- стабильный referralCode пригласившего;
- `inviterSubject → inviteeSubject`, канал, cohort/campaign, время и версия правила;
- захват кода до регистрации с переносом через Telegram/Identity;
- проверка существования пригласившего, запрет самоприглашения, повторов и циклов;
- уже сохранённая связь не переписывается автоматически;
- invitation для доступа к Workspace и referral для атрибуции не смешиваются;
- первая предложенная политика: сохранять первое подтверждённое допустимое приглашение. Это предложение, а не уже принятое правило.

Можно начать с одной линии приглашения и метки марафона. Расчёт комиссий, многоуровневые выплаты и доли союзов не требуются для сохранения исходных фактов. Их добавление потребует принятой экономики.

## 5. OpenRouter: автоматизация возможна

Официальная документация прямо описывает выдачу отдельного ключа каждому клиенту SaaS.

| Действие | API |
|---|---|
| Создать ключ | `POST /api/v1/keys` |
| Прочитать usage/limit ключа | `GET /api/v1/keys/{hash}` |
| Изменить лимит, отключить | `PATCH /api/v1/keys/{hash}` |
| Удалить ключ | `DELETE /api/v1/keys/{hash}` |
| Проверить общий запас аккаунта | `GET /api/v1/credits` |

Нужен отдельный Management API key. Он управляет ключами и не служит ключом генерации. Новый секрет возвращается только при создании. Для фиксированного предоплаченного бюджета нужен `limit_reset: null`; ежедневный или месячный reset возобновлял бы бюджет без нового пополнения.

Источники: [Management API](https://openrouter.ai/docs/guides/overview/auth/provisioning-api-keys), [создание](https://openrouter.ai/docs/api/api-reference/api-keys/create-a-new-api-key), [изменение](https://openrouter.ai/docs/api/api-reference/api-keys/update-an-api-key), [официальный сценарий ключа на клиента](https://openrouter.zendesk.com/hc/en-us/articles/51680687417499-Can-I-create-one-API-key-per-user-with-its-own-spending-limit-Management-API-keys).

### Предложенный процесс

1. Пользователь входит и завершает onboarding; бесплатный денежный лимит автоматически не обещается.
2. После договорённости оператор фиксирует подтверждённое пополнение: кто, сумма/валюта, согласованный AI-бюджет в USD, основание, дата и уникальный ID операции.
3. Сервер создаёт ключ либо повышает существующий накопительный лимит; сохраняет key hash и зашифрованный secret.
4. Ключ автоматически прикрепляется к личному IP Workspace через серверный сервис. В браузер передаются статус и остаток.
5. UI показывает доступный AI-бюджет и расходы; при исчерпании предлагает обратиться за пополнением.

Пользователю ключ не требуется: выдача его наружу позволяет тратить средства вне продукта и делает продуктовую статистику неполной. Management secret должен быть доступен только операторскому provisioning-модулю; обычные web/worker получают лишь нужные generation credentials.

Пример: лимит был $10, потрачено $6, осталось $4. Подтверждённое пополнение AI-бюджета ещё на $5 означает новый накопительный лимит $15 и остаток около $9. Нельзя установить лимит $5 или заменить его на `usage + 5`, потеряв старый остаток.

Все ключи расходуют один общий баланс OpenRouter. Лимит ключа не резервирует для него деньги. Пользовательское пополнение, выделенный AI-бюджет и фактический provider cost должны быть разными записями. Конвертацию рублей, комиссии и возможную наценку фиксировать явно для каждой операции; их правила пока не утверждены.

### Что обязательно учесть

- Идемпотентный журнал пополнений; повтор запроса не добавляет деньги повторно.
- Последовательная обработка изменений бюджета одного аккаунта; сериализовать конкурентные top-up.
- Абсолютный целевой лимит выводится из журнала, а не вычисляется повторным прибавлением при каждом retry.
- Состояния provisioning: pending, applied, failed/needs-review и readback.
- Если создание ключа прошло, а ответ потерян, не создавать ключи бесконтрольно повторно. Сверить по идентификатору операции; потерянный plaintext не восстанавливается через GET, потребуется отзыв найденного orphan и контролируемая замена.
- Общий остаток проверяется операторским модулем; дочерний generation key не заменяет Management key.
- Вводится режим managed connection, чтобы обычная смена/удаление BYOK-подключения не обходила учёт. Изменение поля только в UI недостаточно.
- Лимиты параллельности, размера batch, разрешённых моделей и стоимости операции проверяются сервером.
- При пограничном остатке дорогостоящие задачи не запускаются без резерва/достоверной верхней оценки. Если оценка недоступна, такой сценарий закрывается для пилота.
- Повтор платного dispatch после неоднозначного сетевого ответа не должен создавать двойную генерацию.

OpenRouter предупреждает, что большой запрос или параллельные запросы могут немного превысить лимит до записи окончательной стоимости. Поэтому его cap — дополнительная защита, а не точный банковский остаток: [объяснение OpenRouter](https://openrouter.zendesk.com/hc/en-us/articles/51690568268059-How-do-I-cap-my-spending-and-stop-runaway-usage-from-coding-agents).

Важная текущая граница: [Ask AI использует отдельный env-ключ](/Users/m.pyzhov/WORKSPACEs/Development/PRODaction/image-prodaction/Repos/image-prodaction/src/modules/chat-assistant/server/composition.ts:114), а генерации — connection Workspace. Нужно либо перевести расходы Ask AI на выбранного финансового владельца, либо явно выделить ограниченный бюджет поддержки за счёт платформы. Одного персонального ключа для полного учёта всех расходов сейчас недостаточно.

Владение provisioning и журналом пополнений должно быть платформенным модулем с отдельным контрактом. Для пилота достаточно закрытой операторской команды/экрана и небольшого модуля; не требуется большая админка, отдельный микросервис или подписки. Image Production остаётся потребителем разрешённого бюджета и владельцем execution usage. Точное размещение модуля фиксируется ADR до реализации.

## 6. Короткий onboarding и измерение

Предложенный путь рассчитан на достижение результата, ориентир — несколько минут; время нужно измерить на тестовых людях.

1. Вход email или Telegram. Объяснение, что аккаунт общий.
2. Имя и название личного пространства. Данные, уже полученные из Identity, подставляются.
3. Три коротких вопроса: роль/занятие, опыт AI, основная цель. Дополнительные сведения можно пропустить.
4. Готовый пример: открыть шаблон → изменить запрос → запустить → сохранить/скачать результат.
5. Видимый остаток бюджета, краткая инструкция и доступ к помощи.

Анкета сохраняется на сервере с версией и прогрессом. После обновления страницы ответы остаются, завершённый тур не начинается заново. Основные поля редактируются позже. Маркетинговое согласие отдельно и по умолчанию выключено; email не становится обязательным для Telegram-входа.

План данных:

- глобальный subject, product user ID, workspaceId;
- имя/роль, уровень опыта и цели;
- продукт, версия анкеты, startedAt/completedAt;
- cohort марафона, источник и referral attribution;
- отдельные поля для фактов пользователя и последующих аналитических выводов.

Минимальные события: signup_completed, product_login_succeeded, workspace_created, onboarding_started/completed/skipped, generation_requested/succeeded/failed, asset_saved/downloaded, topup_confirmed. Где возможно, результат фиксирует сервер; повтор события имеет eventId.

Первые метрики: вход → onboarding → первая успешная генерация → сохранённый результат; время до результата; стоимость успешного результата с учётом неудачных попыток; ошибки входа/генерации; повторный визит на следующий день. По каждому платному действию нужны provider/model, стоимость, результат и финансовый владелец. API-ключи, пароли и полный пользовательский prompt в аналитические события не передаются.

Текущий IP SSO теряет исходный адрес: callback настроен на successPath `/`. Legacy email login умеет читать `next`, но Identity-путь его не переносит. Нужно хранить безопасный локальный returnTo в серверной попытке входа, провести его через onboarding и открыть исходный экран. Произвольный внешний URL принимать нельзя.

## 7. Последовательность работ

Оценки ниже — ориентиры инженерного труда по результатам просмотра, без учёта ожидания DNS/SMTP, новых UI-макетов и обнаруженных регрессий. Они не являются обещанием дедлайна.

| Этап | Работа | Готовность проверяем так | Ориентир |
|---|---|---|---|
| 0 | Зафиксировать scope существующих изменений, адреса, пилотный сценарий и объём аудитории | Один определённый release candidate и маршрутная схема | 0,5–1 ч |
| 1 | Устранить IP CI blocker, синхронизировать Identity client, проверить standalone поставку Identity и параметры IP | Чистая установка/сборка, необходимые gates, миграции на тестовой БД | 3–6 ч |
| 2 | Настроить production Identity, email и Telegram, проверить returnTo и личный Workspace | Два новых независимых пользователя проходят сквозной вход, чужие данные недоступны | 3–5 ч |
| 3 | Managed keys + операторское пополнение + ограничения расходов | Два бюджета независимы; повтор top-up безопасен; zero/low balance закрывает платный dispatch | 3–6 ч |
| 4 | Анкета, короткий тур, шаблон, события; минимальная referral attribution | Новый участник самостоятельно получает результат; ответы и источник сохраняются | 3–5 ч |
| 5 | Финальная приёмка, backup/restore, deploy и проверка после выпуска | Production-сценарий подтверждён на выпущенной версии, rollback известен | 2–4 ч |

Суммарно примерно 15–27 часов инженерной работы даже без широкой переработки интерфейсов. Поддержка `/production` добавляет отдельный объём адаптации/проверок, предварительно ещё 2–5 часов; общий canonical Workspace и полноценный кошелёк экосистемы сюда не включены. Часть инфраструктурной работы может идти одновременно с продуктовой; зависимости всё равно должны пройти в указанном порядке.

Поэтому к завтра разумно целиться в закрытый пилот с личным Workspace, узким набором моделей, одним простым учебным примером и операторским пополнением. Если полный строгий список обязателен, нужен пересмотр срока, а не формальное объявление readiness.

Операторское подтверждение денег можно оставить ручным действием, автоматизировав создание/подключение ключа и изменение лимита. Так пользователь получает удобный сценарий без разработки платёжного шлюза.

Реферальная атрибуция не должна теряться у первой группы. Если серверная связь ещё не готова, запуск по персональным реферальным ссылкам не объявлять готовым; согласовать только cohort-метку либо завершить минимальный модуль до приглашения участников.

## 8. Инфраструктура, которую можно готовить сейчас

- Один внешний HTTPS-прокси на сервер, отдельные upstream для IP web и Identity.
- IP: web, generation worker, pipeline worker, PostgreSQL, приватное объектное хранилище.
- Identity: собственный процесс/container и отдельная PostgreSQL база с отдельным пользователем. Один PostgreSQL cluster допустим при разделении баз/прав; это не означает общие продуктовые таблицы.
- SMTP с рабочей доставкой подтверждения/сброса; бот и согласованный владелец webhook.
- Секреты через защищённое окружение/хранилище, без переноса dev-баз и dev-ключей по умолчанию.
- Точные внешние callback и issuer; SSO backend должен разрешать тот же стабильный issuer, который видит браузер.
- Стабильные Compose project/service names, resource limits для тяжёлых media workers, журналирование и backups вне единственного рабочего volume.
- Политика доступа: приглашённый пилот/контролируемый signup; автоматического положительного бюджета при регистрации нет.
- Реальное число пользователей, модели и параллельность нужны для sizing. Проверка localhost не доказывает производительность машины пользователя.

В существующем IP [production Compose](/Users/m.pyzhov/WORKSPACEs/Development/PRODaction/image-prodaction/Repos/image-prodaction/compose.production.yaml:3) нет передачи REVERIE_IDENTITY_ISSUER/CALLBACK, регистрация по умолчанию закрыта, email transport выключен. Это старый release-контур: без обновления он не включает новую программу запуска. Сам Identity в проверенных Compose-файлах ещё не имеет готовой выделенной production-поставки.

При последующих локальных rebuild IP необходимо сохранить сеть Content Hub через compose.integration.yaml и проверить соединение из Hub. При работе с Docker сначала/после фиксировать диск, сборки и объекты проекта согласно AGENTS. Аудит Docker-объекты не менял.

## 9. Условия допуска первых пользователей

- Версия приложения зафиксирована и соответствует проверенной сборке.
- Email-регистрация/подтверждение/reset и Telegram login проходят на реальных HTTPS-адресах.
- Повторный вход узнаёт того же человека; чужой email не объединяет аккаунты.
- Workspace создаётся один раз; пользователь A не читает проект, ассет, чат, usage или ключ пользователя B.
- Исходная ссылка восстанавливается после входа и onboarding.
- Referral/cohort и ответы анкеты сохраняются повторобезопасно.
- Подтверждённое пополнение один раз меняет бюджет; ключ остаётся только на сервере.
- Остаток и ограничения корректны для генераций и выбранной политики Ask AI.
- Успешная генерация сохраняется, переживает перезапуск и скачивается; неуспешная не списывается повторно приложением.
- Исчерпание бюджета, ограничения параллельности и неоднозначный upstream ответ обработаны явно.
- Проверены backup/restore и блокировка участника; после переключения версии проверен живой сценарий.
- Приёмочная платная генерация проводится отдельным согласованным бюджетом; в ходе этого аудита её не было.

## 10. Основа для Content Hub на следующей неделе

Сейчас заложить стабильный issuer и subject, конфигурируемые product URLs, правила Workspace mapping, общий финансовый идентификатор, разделение usage по продуктам, account-profile и referral contracts. Общая навигация использует реальные URL, сервер каждого продукта проверяет собственный доступ.

Далее: включить Hub как OIDC consumer, завершить общий Workspace contract/provisioning, проверить новые пространства и Runtime v2 grants/capability bindings, обеспечить межпродуктовый revoke, агрегировать бюджет и профиль в общем view. Доступ Hub к IP выдаётся сервисными полномочиями и закреплёнными версиями pipeline, не cookie владельца и не ссылкой на canvas node.

Публичная витрина рецептов, LMS, многоуровневые выплаты, тарифы подписок и полная операторская админка остаются отдельными этапами согласно принятому решению.
