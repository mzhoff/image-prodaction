## Контур и установка счётчика

1. В [Метрике](https://metrika.yandex.ru/) выбрать «Добавить счётчик».
2. Имя текущего счётчика: **REVERIE Production**. Адрес сайта:
   `production.apption.space`. Часовой пояс: `Europe/Moscow`.
3. Включить «Принимать данные только с указанных адресов сайтов». Не добавлять
   localhost, IP сервера, Identity или Content Hub. Не включать поддомены.
4. Вебвизор включён в счётчике; приложение разрешает запись только маскированной
   анкеты `/onboarding` без query/hash. Выключить карты кликов/ссылок, запись форм, контентную аналитику,
   Ecommerce, автоматические цели, Advanced Matching/дополнительные настройки
   отслеживания и сохранение маскированных контактных данных. Наши события
   отправляются явно. Настройки доступны в [разделе счётчика](https://yandex.ru/support/metrica/ru/general/counter-general).
5. Передать разработчику только числовой ID счётчика. Он не является секретом.
   Не вставлять второй стандартный snippet в страницу: это даст дубли просмотров.
6. Создать целевые события из таблицы ниже и проверить на одном тестовом
   аккаунте. Затем включить beta-конфигурацию и зафиксировать фактическую дату
   старта сбора как `analytics_started_at` в журнале выпуска.

На `localhost`, `127.0.0.1`, Visual Intent и в тестах реальная отправка запрещена
проверкой окружения и allowlist hostname. Локальная отладка использует mock/debug
приёмник без загрузки внешнего SDK. Сейчас единственный разрешённый production
hostname — `production.apption.space`. При переходе на официальный домен его
можно явно добавить или заменить в настройках счётчика и allowlist приложения;
новый счётчик не обязателен. Дату перехода фиксируем, внутренние тесты не
смешиваем с бетой и публичным релизом.

## Что и как отправлять

### Runtime-конфигурация

`METRICA_MODE=off|debug|live`, `METRICA_COUNTER_ID=<числовой ID>`,
`METRICA_ALLOWED_HOSTS=production.apption.space` — серверные переменные,
передаваемые в web-контейнер через `compose.production.yaml`. Номер счётчика
публичный; OAuth-токен управления Метрикой приложению не нужен. Настройки
читаются при запросе страницы через Next `connection()`, а не встраиваются
в образ при сборке. После изменения окружения нужен перезапуск web с полным
набором действующих overlays; секреты и остальные сервисы не менять.

Без явной настройки в production сбор выключен. В development по умолчанию
действует `debug`: очищенные команды видны в консоли браузера с префиксом
`[behavioral-analytics]`. Явный `METRICA_MODE=off` отключает и отладку.
`live` требует валидный ID, HTTPS и точное совпадение hostname с allowlist;
localhost/127.0.0.1/::1 не отправляют реальные события даже при live-настройке.
SDK загружается на разрешённых страницах продукта и анонимного входа /login, /register. Callback, reset-token и страницы с письмами исключены.

Модуль: `src/shared/analytics/`; Next-композиция: `src/app/analytics/`.
Очередь ожидания SDK ограничена 100 записями, очищается при выходе/смене
аккаунта; ошибка транспорта не выбрасывается в продуктовый обработчик.
До входа разрешена только воронка авторизации на очищенных маршрутах.

Доступ к продуктовым страницам проверяет сервер. Счётчик использует ClientID и не зависит от повторного клиентского запроса сессии. Дополнительный необязательный запрос `/api/account/analytics-profile` возвращает внутренний UserID и разрешённые категории анкеты.
Аналитика не влияет на права, баланс, выполнение AI-запросов или результат входа.
Ошибки/блокировка SDK не должны ломать продукт.

### Инициализация и страницы

Используем SPA-режим `defer: true`, чтобы не отправлять автоматический первый
просмотр. Изменения маршрута фиксируются явным `hit`; открытие/закрытие меню,
движение canvas и autosave не являются просмотрами.
[Официальный SPA-контракт](https://yandex.ru/support/metrica/ru/code/counter-spa-setup).

```js
ym(counterId, 'init', {
  defer: true,
  sendTitle: false,
  webvisor: false, // true только на маскированной /onboarding без query/hash
  clickmap: false,
  trackLinks: false,
  trackHash: false,
  accurateTrackBounce: false,
  ecommerce: false,
  disableYtm: true,
});
```

`sendTitle: false` отключает автоматическую запись заголовков. Опции `url` и
`referrer` не описаны в актуальной таблице `init`; на них нельзя опираться как
на подтверждённый механизм очистки данных.
[Параметры инициализации](https://yandex.ru/support/metrica/ru/code/counter-initialize).

Для каждого `hit` явно задаются безопасные URL, `title` и `referer` — именно с
одной `r` внутри имени `referer`. Без явного URL/title SDK использует адрес и
заголовок браузера. Документ представляется шаблоном `/projects/:document`,
а имя документа и его ID в URL не передаются. Query и hash отбрасываются,
неизвестный маршрут не отправляется либо получает заранее определённое общее
имя. Источник перехода — предыдущий очищенный маршрут, не `document.referrer`.
[Контракт hit](https://yandex.ru/support/metrica/ru/objects/hit).

`ip_page_view` — внутреннее имя события адаптера; в Метрике это `hit`, а не
дополнительный `reachGoal` с тем же смыслом.

Указанные меры контролируют наши payload. Они не доказывают отсутствие всех
служебных запросов SDK, cookies или браузерного HTTP Referer. Перед реальным
включением проверить Network, включая загрузку SDK, события, переходы и выход.
Вебвизор включается только для анкеты: body маскирован, статический интерфейс
анкеты открыт для записи, свободные поля и ошибки скрыты. На остальных страницах
работают только события. Маскирование в реальной записи проверяется после выпуска.

### Пользователь и выход

После отдельного запроса пользователя 22 сентября добавлен `setUserID` с
`ip_<внутренний user.id продукта>`. Это псевдонимный, а не анонимный идентификатор:
его можно сопоставить с нашей БД. Имя, email, телефон, Telegram/Workspace ID,
точный возраст и свободные ответы не передаются. Авторизованный сервер выдаёт
только профиль текущего пользователя; браузер повторно проверяет список полей.

`userParams` получает `UserID` и `reverie`: возрастную группу, роль, формат работы,
размер команды, отрасль, опыт AI/агентов, автоматизацию и фиксированные флаги
целей/задач/инструментов. Незавершённая анкета не превращается в готовый сегмент.
Параллельно `params.audience` сохраняет категории на визите. Параметры посетителя
могут применяться к истории: это текущий профиль, а не история изменений.
Бюджет, права и материалы остаются в собственной базе.
[Ограничения параметров посетителей](https://yandex.ru/support/metrica/ru/data/user-params-data).

Сквозной браузер → бот связывается ClientID. При выходе/смене аккаунта очередь
и профиль очищаются. Общий браузер и разные устройства всё ещё требуют
осторожной интерпретации; точное число аккаунтов считаем в своей БД.
Подробный контракт и правила Вебвизора: [онбординг](analytics-onboarding-contract.md).

### Минимальные события

Все имена версионируются общим `event_schema`, не переименовываются после
начала сбора. Общие поля: `product: 'image-production'`, `event_schema: 2`,
`environment: 'beta' | 'local'`,
`screen` из фиксированного списка экранов.
`local` используется только в отладке без сети. Дополнительные разрешённые
поля — `source`, `node_type`, `operation` с ограниченными значениями.
Workspace ID, document ID, числовые снимки документов и произвольные объекты
модели, ошибки или формы в первом проходе не отправляются.

| Событие | Когда считать | Что означает / что не означает |
| --- | --- | --- |
| `ip_app_opened` | Один раз после определения авторизованного пользователя на загрузку страницы | Открытие приложения с сессией; не новая регистрация и не визит Метрики. Reload может дать новое событие в том же визите |
| `ip_page_view` | Переход на новый разрешённый маршрут | Только `hit` с безопасным URL; без цели-дубля |
| `ip_document_opened` | Документ успешно загружен и доступен пользователю | Реальное открытие редактора, не просто переход по ссылке и не каждый render |
| `ip_document_created` | Создание документа завершилось сохранением | Успешное создание; не нажатие Create до ответа сервера |
| `ip_document_imported` | Файл разобран и граф применён в редакторе | Импорт в текущий граф; не подтверждение сохранения в БД или создания нового документа |
| `ip_document_exported` | Экспорт подготовлен и передан механизму скачивания | Не подтверждает, что пользователь сохранил файл на диск |
| `ip_node_added` | Пользователь добавил ноду в граф | Разрешённый `node_type`; не replay загрузки, autosave или перемещение ноды |
| `ip_generation_requested` | Пользователь отправил запрос на генерацию | Намерение/запуск; не успешный результат, оплаченная операция или её стоимость |
| `ip_assistant_opened` | Панель ассистента перешла в открытое состояние, включая автоматическое открытие | Показ панели, а не обязательно намеренное действие; не каждый render открытой панели |
| `ip_assistant_message_sent` | Сообщение передано обработчику отправки | Попытка обращения; без текста, файлов, URL и без обещания успешного ответа |

Цели нужны для девяти событий, отправляемых через `reachGoal`; `ip_page_view`
исключён. Для каждой: «Цели → Добавить цель → Целевое событие → совпадает» и
точное имя из таблицы. Цель создаётся до приёмки потока. Не назначать фиктивную
денежную стоимость генерации/сообщению.
[Целевое событие](https://yandex.ru/support/metrica/ru/general/goal-js-event),
[reachGoal](https://yandex.ru/support/metrica/ru/objects/reachgoal).

Достижения цели — наблюдаемая браузерная активность. Это не бухгалтерия
документов: блокировщик, сеть, повтор, быстрые однотипные действия и лимиты
Метрики искажают точные количества. Число существующих/созданных документов
по владельцу и Workspace считается из серверной БД. `document_count` в первом
проходе не передаётся. Импорт не увеличивает этот счётчик сам по себе.
Реальное выполнение/стоимость генераций — из durable execution и usage.

## Пять рабочих дашбордов

Отчёты строятся по анонимному пути, шагам и placement-параметру `source`.
Конкретного человека и его ответы ищем только в собственной базе, не в Метрике.

Ниже — целевая схема отчётов; фактически сохранённый стартовый набор приведён
отдельно. Числитель и знаменатель считать за один период, в одном сегменте и с
одинаковой моделью посетителей. На старте — 7/28 дней, абсолютные числа рядом
с процентами.

| Дашборд | Основные виджеты и определения | Цели / сегменты |
| --- | --- | --- |
| **1. Бета: активность** | Авторизованные посетители по дням; активные за 7 и 28 дней; нативные визиты Метрики на посетителя; браузер/устройство. DAU/WAU — наблюдаемые посетители, не число учётных записей. WAU не сумма семи DAU; app_opened — отдельное число открытий/перезагрузок | `ip_app_opened`; beta host; посещения и возвращаемость — по нативным визитам, не reaches этой цели |
| **2. Первый полезный путь** | Воронка: app opened → document opened → node added → generation requested; отдельная ветка через assistant message. Называть «дошёл до запроса генерации», пока нет события подтверждённого результата | Воронка в UI с выбранным порядком/окном. Сравнение новых для счётчика посетителей и повторных; не называть первые визиты регистрациями |
| **3. Документы и экспорт** | Число пользователей, создававших/импортировавших/экспортировавших; достижения каждой цели отдельно; экспортировавшие / открывавшие; открытия на посетителя | `ip_document_opened/created/imported/exported`; экран editor. Точные document counts — отдельный серверный отчёт, не goal totals |
| **4. Возможности студии** | Пользователи по node_type; доля видевших панель ассистента; доля отправивших сообщение среди видевших; запросы генерации на посетителя; сравнение выбранных недель | `ip_node_added`, `ip_generation_requested`, `ip_assistant_opened/message_sent`; показ ассистента включает auto-open и не доказывает спрос на него |
| **5. Возвращаемость** | D1/D7 и W1/W2 по дате первого измеренного посещения; размер когорты; доля возвращавшихся; отдельно возвращавшиеся с действием, если это поддерживает выбранная настройка отчёта | UI «Отчёты → Retention», cohort первого визита, выбранные календарные или 24-часовые окна. Возврат и действие — разные показатели |

считает последовательность `app_opened → document_opened → node_added →
generation_requested` с ограничением **24 часа**, разбивкой по типу устройства.
Это путь до запроса генерации; готовый шаблон без добавления ноды или работа
через ассистента не обязаны проходить эту воронку. График «Пользователи по этапам»
сравнивает аудитории событий без требования последовательности.

`tableGroupByInterval=day`, метрики процента и количества вернувшихся.
Новые — по первому измеренному визиту, не по регистрации аккаунта.
После появления событий остаётся настроить разрезы `source`/`node_type`,
проверить их на реальных значениях, дополнить недельными когортами и веткой
воронки через ассистента. Эти разрезы ещё не проверены на принятых данных.

Автоцели, запись форм, clickmap, Ecommerce и Tag Manager отключены
и проверены через Management API. Вебвизор разрешён счётчиком; область записи
ограничена кодом приложения до маскированной анкеты. В UI включён приём только с указанного
адреса без поддоменов; дополнительные настройки отслеживания, контентная
аналитика и доступ к рыночным отчётам выключены. Отключение этих опций не
заменяет проверку фактических сетевых запросов SDK при публикации.

В API для целей доступны `ym:s:goal<goal_id>users` (посетители), `visits`
(визиты с целью), `reaches` (достижения). Числовой goal_id берётся из реального
реестра, а не из строкового имени JavaScript-события.
[Метрики конверсий](https://yandex.ru/dev/metrika/en/stat/metrics/visits/conversions).

### Retention без выдуманной истории

Встроенные когортные отчёты группируют посетителей по первым визитам; фильтры
Retention применяются к первым визитам когорты. Доступны календарные и
24-часовые окна. В документированной общей справке Retention нет требования
покупать Про; пакет Про расширяет квоты, а не блокирует существующие отчёты.
[Retention и когорты](https://yandex.ru/support/metrica/ru/reports/retention-cohorts),
[Метрика Про](https://yandex.ru/support/metrica/ru/pro/intro).

Установленный сегодня счётчик ничего не знает о прошлых входах. Участники старой
беты попадут в «первый измеренный визит», хотя аккаунты могли существовать ранее.
Подпись к отчёту должна содержать дату начала сбора. D7 показываем только для
когорт, у которых прошло семь полных дней; более молодые ячейки — «ещё рано»,
не ноль. Нельзя вычислить retention регистрации делением недельного users на
дневной users. Для строгого account-based retention нужны серверная дата
регистрации и история событий с тем же account ID; такой отчёт здесь не обещан.

## Что доступно через API и что настраивается в интерфейсе

Подключённый MCP-каталог проверен read-only через `ym_search`:

- `counters`, `counter`, `goals`, `segments` читают счётчики, настройки, цели и
  API-сегменты. Настройка целей и сегментов уже входит в запрос пользователя:
  после получения counter ID и доступа можно использовать `goal_create` и
  `segment_create`, сначала проверив существующие объекты, чтобы не дублировать их.
  Все 46 целей существуют; ID сохранены в реестре выпуска. Созданы 28 API-сегментов
  и 23 сегмента в интерфейсе для категорий анкеты. Это разные списки Метрики;
  API-сегменты не появляются автоматически в пользовательском списке.
  Выбор 23 сегментов REVERIE проверен непосредственно в отчёте воронки.
- `stat_data`, `stat_data_bytime`, `stat_data_comparison` читают агрегаты,
  временные ряды и сравнения. Доступные поля/сочетания проверяются на реальном
  счётчике; учитывать sampling, период, часовой пояс и пустые значения.
- Создание пяти дашбордов/виджетов и настройка Retention — через интерфейс.
  В обнаруженном каталоге нет отдельного dashboard/retention API action;
  не выдавать обычную таблицу API за готовый сохранённый дашборд или retention.

Для базовой Метрики документированы лимиты: 5 пользовательских дашбордов, 30 виджетов на каждом, 200 целей,
500 сохранённых сегментов, 1000 событий на визит. Та же цель учитывается не
чаще раза в секунду; онлайн-достижений целей — до 400 за визит. Поэтому не
отправляем mousemove, pan/zoom, каждый keystroke, polling и autosave.
[Общие лимиты](https://yandex.ru/support/metrica/ru/general/limits),
[лимиты целей](https://yandex.ru/support/metrica/ru/general/goal-js-event).

В текущем UI лимит создания уже достигнут (пять пользовательских плюс стандартные);
новые воронки добавлены на существующий дашборд без удаления старых виджетов.

Про даёт до 100 дашбордов и 1000 целей/сегментов. Для описанного бета-набора
покупка пакета из-за этих лимитов не требуется.
[Лимиты Про](https://yandex.ru/support/metrica/ru/pro/limits).

## Приёмка перед сбором беты

- ID и домен относятся к новой бете; реальные цели существуют с точными именами.
- На localhost/Visual Intent нет запросов к Метрике даже после входа и действий.
- В разрешённом beta-host одна навигация даёт один очищенный hit; render,
  autosave и смена выделения не размножают события.
- Проверены init, hit, reachGoal и logout в Network: нет имени,
  email, Telegram ID, prompt, chat text, имени документа, исходных URL, query,
  hash и OAuth-кодов в наших данных. Проверены также служебные запросы SDK.
- Выход/смена аккаунта не отправляют очередь старого пользователя от имени нового.
- Отключённый SDK/блокировщик не мешает продукту; пользователь не ждёт аналитику.
- Отчёт сверяется с несколькими известными действиями; ноль до поступления
  первых данных не считается доказательством отсутствия активности.
- Зафиксированы дата старта сбора, версия схемы и ограничение точности.
