# REVERIE: публичный сайт экосистемы и community MVP

Дата исследования: 2026-09-08.
Статус: предложение к реализации по запросу владельца; не выполненная интеграция и не изменение утверждённых платформенных документов.

Обновление после обратной связи владельца: сайт разрешено скопировать, выбран отдельный
репозиторий `../reverie-site` с собственным контейнером и Visual Intent. Исходник сохранён.
Новые названия продуктов, независимость standalone ChatModule, приватный кабинет,
opt-in creator profile, гибкий домен и уточнения метаданных зафиксированы в
`../reverie-site/docs/ecosystem-direction.md` и `publication-metadata.md`.
Эти уточнения заменяют противоречащие им предложения ниже, в частности обязательную
публичность всех prompts/моделей и сохранение сайта в старом монорепозитории.
Остальная backend/SSO/community-интеграция остаётся планом, не выполненной работой.

## 1. Рекомендуемое решение

Развивать существующий `apps/site-web` в репозитории REVERIE как публичный сайт экосистемы. Сохранить его визуальную основу и самостоятельную сборку. Подключить к актуальному Content Hub через HTTP-контракты. Галерею, публичные профили и челленджи реализовать как отдельный community-модуль в серверном приложении Content Hub. Image Production остаётся владельцем создания материалов, исходников и execution provenance.

Для размещения достаточно одного публичного IP и одного входного Caddy на HTTP/HTTPS. Продукты получают поддомены; публичные разделы — пути основного сайта. Внутренние приложения работают в контейнерах с адресами сервисов. Дополнительные публичные IP и отдельный публичный порт для каждого приложения не требуются.

Это план интеграции в существующих репозиториях. Он не требует копирования проекта, новых worktree, переноса старого backend REVERIE или слияния баз данных.

## 4. Адреса и размещение

Ниже предлагаемые адреса на уже используемом в конфигурации домене; это не текущая DNS-конфигурация и не команда переключения.

| Адрес | Назначение | Обработчик |
|---|---|---|
| `reverieapp.ru` | главная, продукты, блог, академия, сообщество | существующий `site-web` |
| `reverieapp.ru/products/content-hub` | описание Content Hub | `site-web` |
| `reverieapp.ru/products/image-production` | описание Image Production | `site-web` |

| `reverieapp.ru/gallery`, `/works/{id}` | лента и страница работы | `site-web` + community API |
| `reverieapp.ru/creators/{slug}` | портфолио и услуги специалиста | `site-web` + community API |
| `reverieapp.ru/challenges/{slug}` | челлендж и конкурсные работы | `site-web` + community API |

| `app.reverieapp.ru` | Content Hub / кабинет | текущая админка Content Hub |
| `studio.reverieapp.ru` | Image Production | текущий Image Production web |
| `auth.reverieapp.ru` | целевой единый вход | Identity composition; требует реализации |

`media` и отдельный `api` поддомены добавляются по необходимости; для первого API достаточно `/api/public/v1` на главном сайте с узкой маршрутизацией.

Публичные DNS A-записи основных имён могут указывать на один IP. AAAA добавляется только при работающем IPv6. Caddy принимает HTTPS на 443, HTTP на 80 переводит на HTTPS и обслуживает сертификаты. Внутри Docker разные контейнеры могут одновременно слушать порт 3000: имена сервисов различаются. При размещении процессов без контейнерной сети им потребуются разные loopback-порты, но посетители их не увидят.

Один общий edge должен владеть 80/443. Текущие два production Compose нельзя просто запустить рядом с обоими Caddy на этих портах. План развёртывания должен подключить существующие приложения к общей edge-сети, сохранив отдельные приватные сети БД и хранилищ. Сервисы должны иметь уникальные сетевые alias, например `reverie-site`, `content-hub-api`, `image-production-web`.

Для первого запуска можно оставить все процессы на одной машине с ограничениями CPU/RAM и конкуренции задач. Медиаобработка не должна вытеснять сайт и БД. Один сервер остаётся общей точкой отказа; восстановление требует off-host backup БД, файлов и конфигурации. Резервный volume на том же диске не защищает от потери машины.

Ресурсы сервера, свободный диск, текущая нагрузка, доступность хранилища и стоимость трафика не измерены. Гарантировать ёмкость или назвать срок выкладки по этой проверке нельзя. GPU для обращений к внешним AI-провайдерам не требуется; локальные модели данным MVP не предусмотрены.

## 5. Владение данными и кодом

| Часть | Где развивается | Ответственность |
|---|---|---|
| Публичный интерфейс | существующий REVERIE `apps/site-web` | страницы, поисковая выдача, навигация, формы, share preview |
| Редакционный контент | Content Hub | описание продуктов, блог, уроки, кейсы, публикационный lifecycle |
| Community, логический модуль | Content Hub API | публикации в галерее, профили, услуги, голоса, челленджи, модерация |
| Производство | Image Production | исходники, графы, результаты, фактические модели/prompts и происхождение |
| Identity | узкий общий платформенный контур | principal, связь существующих аккаунтов, сессии и полномочия |
| AI-помощник | ChatModule с адаптерами продуктов | диалоги, действия и объяснения в контексте пользователя |

Размещение community в Content Hub — предложение этого плана. Модуль получает отдельные contracts/core/adapters и таблицы; публичные работы не следует превращать в обычные BlogPost только ради повторного использования CMS. Отдельный микросервис для голосов или профилей в MVP не нужен.

Глобальная лента объединяет только явно опубликованные community-записи. Она не делает запросы ко всем приватным Workspace. Автор профиля привязан к человеку; право опубликовать командную работу проверяется отдельно по владельцу исходника и полномочиям Workspace.

## 6. Единый вход

Общие поддомены и одинаковая библиотека Better Auth не создают общий аккаунт автоматически. Нужен общий issuer и явное сопоставление существующих пользователей/Workspace с сохранением их ID. Нельзя связывать независимые аккаунты лишь по совпадению неподтверждённого email.

Рекомендуемый старт: Identity composition на стороне центральной платформы Content Hub, сначала для сайта и Content Hub; Image Production подключается как клиент общего входа через стандартный OAuth/OIDC-контракт. Локальные product cookies сохраняют собственные имена и host scope; общая parent-domain cookie не является заменой SSO.

Публичное чтение не требует входа. Голосование, редактирование профиля и публикация требуют подтверждённой сессии. Пользователь, который только голосует, не должен автоматически получать доступ в клиентский Workspace или платное рабочее место. Текущее создание Workspace после регистрации Content Hub нужно проверить для такого типа участника.

Маркетинговый сайт можно выпустить до SSO. Для полного пути «создал в Studio → опубликовал → появилось в моём портфолио» потребуется проверенная связь пользователя между продуктами. Полную миграцию identity нельзя прятать внутри задачи оформления кнопки входа.

## 7. Публичная работа и портфолио

Минимальная карточка работы:

- стабильный public ID, название, описание, дата;
- автор/соавторы и ссылка на портфолио;
- выбранные теги;
- модель либо список моделей, использованных на выбранных этапах;
- публичный prompt и пояснение процесса;
- изображение/превью, размеры, alt;
- указание REVERIE / Image Production;
- условия дальнейшего использования и возможность ремикса, когда она поддерживается.

Фактические данные выполнения и публичное описание процесса хранятся отдельно. Пользователь видит точный состав карточки перед публикацией, включая prompt. Если он сократил или отредактировал prompt, карточка обозначает это; нельзя выдавать его за полный точный запрос выполнения. Для многошаговой работы не следует приписывать весь результат одной модели. Пользовательские теги и описания не считаются автоматически подтверждёнными данными runtime.

Приватный graph, скрытые системные инструкции, credentials, внутренние ссылки на клиентские файлы и вся metadata целиком не входят в публичный контракт. Публикация модели и prompt не требует раскрывать эти данные.

Публичное портфолио специалиста включает имя/псевдоним, аватар, описание, специализации, выбранные работы, перечень услуг, статус готовности брать заказы и выбранный самим автором контакт. В первом MVP «Обсудить задачу» ведёт по этому контакту. Встроенную форму обращения можно подключить к Lead Management отдельным шагом с маршрутизацией именно выбранному специалисту, а не общей команде REVERIE.

Первый MVP не включает расчёты между заказчиком и исполнителем, комиссии, безопасную сделку, арбитраж и пользовательский мессенджер. Услуги представлены как портфолио и контакт автора.

## 8. Путь публикации

1. В Image Production пользователь выбирает конкретный готовый результат и действие «Опубликовать в REVERIE».
2. Сервер проверяет доступ к исходнику; интерфейс показывает будущую карточку, автора, модели, публичный prompt, теги и branded preview.
3. Пользователь подтверждает выбранную версию и публичность. Фиксируются версия согласия, состав публикации, автор и время. Согласие на показ не означает разрешение на любые перепубликации или обучение AI.
4. Сервер создаёт PublicationIntent с idempotency key и проверенным источником. Повторный клик не создаёт дубль.
5. Фоновая задача готовит отдельную публичную производную с водяным знаком, убирает лишние файловые metadata и сохраняет связь с приватным оригиналом. Публичный API получает устойчивый URL этой производной, а не временный адрес приватного исходника.
6. Community сохраняет снимок карточки и публичное разрешение. В пилоте новая работа проходит ручную модерацию; появляется в ленте после одобрения.
7. Возвращается постоянная страница `/works/{id}` с share-картинкой. Портфолио может включать эту публикацию в подборку автора.
8. Отзыв публикации закрывает страницу, API и выдачу public media, запускает очистку кешей. Уже скачанные чужие копии и previews соцсетей нельзя гарантированно отозвать.

Предлагаемые состояния: `pending_review → published / rejected`; из `published` — `withdrawn` автором или `hidden` модератором. Revision содержимого неизменяема, но публикация может быть снята с доступа. Исправления создают новую revision; для конкурсной работы после закрытия приёма действует зафиксированная revision.

Публичную производную следует делать отдельным storage-object с собственной политикой доступа. Это управляемый экспорт выбранного результата; массовое копирование приватной библиотеки не требуется. Оригиналы остаются под текущим владельцем. Удаление исходника, потеря membership и снятие публикации должны иметь явно согласованные lifecycle-правила и тесты, а не неявную зависимость от CDN-кеша.

## 9. Community MVP

В первую рабочую версию входят:

- лента «Новые» и «Популярные за период», фильтры по тегам и моделям;
- карточка работы и портфолио с услугами;
- публикация и отзыв выбранной работы;
- один голос на работу от подтверждённого аккаунта с возможностью отмены;
- один тематический челлендж с дедлайном и понятным правилом выбора;
- жалоба, ручное скрытие/одобрение, журнал решений модератора;
- ссылка наружу и downloadable share-версия с брендингом.

Авторизация сама по себе не устраняет накрутку. Минимум — уникальность голоса в БД, ограничения частоты, запрет самоголосования в конкурсном режиме и ручная проверка аномалий. Победитель фиксируется после закрытия приёма и проверки; «новые» сохраняют отдельную видимость независимо от накопленных лайков.

Для пилота разумно начать с изображений. Видео/аудио, полноценные ремиксы, подписки на авторов, комментарии и персональные рекомендации — последующие расширения. Первый челлендж можно связать со Stories, сохранив связь с производственным пилотом.

## 10. Блог, академия и AI на сайте

Для команды REVERIE нужен отдельный редакционный Workspace и Site-binding. Публикации Юлии остаются в её Workspace. Блог использует существующие возможности публикаций после добавления многосайтового Delivery API.

Академия MVP — каталог учебных материалов и последовательности уроков, связанные с продуктами и примерами работ. Курсы с оплатой, отслеживанием прогресса, тестами и сертификатами требуют отдельного учебного домена и не блокируют публикацию первых уроков.

Предлагаемое смысловое разделение страниц продуктов:

- Content Hub: контекст бренда, идеи, редакционная работа, согласование и публикация материалов.
- Image Production: создание и обработка визуальных материалов, переиспользуемые процессы, сохранённые результаты и история происхождения.
- AI-помощник: помощь в работе с контекстом, объяснение функций и выполнение доступных пользователю действий внутри экосистемы.

Каждая страница показывает задачу пользователя, реальный сценарий, подтверждённые возможности, примеры и точку входа. Дорожная карта помечается как план; маркетинговые цифры и отзывы требуют собственного доказательства.

Описание помощника на сайте не требует немедленно открывать анонимный платный AI-chat. Если позже появится виджет, он использует ChatModule с публичными знаниями, отдельным visitor principal и разрешёнными публичными инструментами. Внутренние диалоги и Workspace-контекст не входят в такой режим.

## 11. Собственный API и share

Следующие маршруты — проектируемый контракт, сейчас не реализованы:

```text
GET    /api/public/v1/works
GET    /api/public/v1/works/{id}
GET    /api/public/v1/creators/{slug}
GET    /api/public/v1/challenges/{slug}
POST   /api/community/v1/publication-intents
POST   /api/community/v1/works/{id}/withdraw
PUT    /api/community/v1/works/{id}/vote
DELETE /api/community/v1/works/{id}/vote
POST   /api/community/v1/works/{id}/reports
```

Чтение published-карточек возможно без аккаунта в пределах лимитов и условий использования. Изменения доступны только проверенному пользователю, а межпродуктовые запросы — ограниченному service account с подтверждённым actor/источником. Контракт включает versioning, pagination, allowlist полей и отзыв доступа к скрытым работам. Внешний API не предоставляет приватный Runtime API или права генерации.

Первая кнопка share использует URL, копирование ссылки, скачивание branded-копии и системный Web Share там, где он доступен. Перед передачей файла проверяется поддержка; пользователь может отменить действие. Соцсети должны получать заголовок, описание и `og:image` в исходном серверном HTML без пользовательской сессии. Истечение подписанной ссылки на приватный файл не должно ломать превью.

Наш API позволяет другим приложениям получать опубликованные работы. Он не заменяет API сторонних соцсетей и не даёт права автоматически писать от имени пользователя. Автопубликация впоследствии подключается через адаптеры Content Hub с авторизацией и возможностями конкретной сети.

## 12. Очерёдность и критерии готовности

| Очередь | Изменение | Как проверяем завершение |
|---|---|---|
| 0. Границы и выкладка | ADR, карта доменов, выбор общего edge, инвентаризация сервера, план старых URL и аккаунтов | известны текущие маршруты/потребители, точные цели миграций и способ возврата |
| 1. Публичный сайт | самостоятельная поставка `site-web`, страницы трёх продуктов, настоящие CTA, корректные метаданные и проверенный контент | HTTPS, мобильная проверка, рабочие ссылки, отсутствие зависимости от старого product-web/BFF |
| 2. Контент сайта | `Site/SiteDomain`, отдельный Workspace REVERIE, Delivery API, блог и начальная академия | две независимые площадки показывают только свой опубликованный контент; draft недоступен публично |
| 3. Участник экосистемы | общий вход для сайта/Content Hub, проверенная связь со Studio, публичный профиль и услуги | один человек сохраняет профиль и авторство между продуктами; голосующий не получает чужие Workspace |
| 4. Галерея | publication intent, публичная производная, карточки с происхождением, согласие, модерация и share | полный путь от выбранного результата до открываемой без входа карточки и её отзыва |
| 5. Челлендж | лента, голосование, дедлайн, модераторское завершение | повтор/параллельность не удваивают голоса; правила результата и состояния проверены |
| 6. Внешние потребители | опубликованный read API, документация и затем нужный social adapter | независимый consumer получает только public DTO; скрытая работа исчезает; публикация в сеть подтверждается remote ID |

Согласование контрактов очередей 2–4 можно вести параллельно с сайтом. Выпуск сайта не обязан ждать всей социальной части. Полный gallery MVP завершён только после очереди 5; статичная сетка карточек не заменяет проверку публикации и голосов.

## 13. Проверки перед внешним запуском

- Сайт имеет собственные lint/typecheck/build gates и поставляется через checks → build → автоматическую доставку; не строим всю старую REVERIE-платформу ради сайта.
- Общие пакеты проходят consumer checks в реальном принимающем приложении, новые миграции — проверку сохранности существующих данных.
- Один участник не может читать/публиковать чужой приватный asset; публичная карточка содержит только подтверждённые поля.
- Retry публикации не создаёт дубли; retry/параллельные голоса не меняют итог больше одного раза.
- Отзыв/модераторское скрытие закрывает страницу, API и media; приватные preview не кешируются как публичные.
- Блог Юлии и Site REVERIE изолированы даже при одинаковом slug статьи. Публичный клиент не выбирает произвольный Workspace.
- Старые ссылки Studio, OAuth callbacks, Runtime consumers и uploads проверены после изменения доменов. Нельзя применять общий 301 ко всем старым POST/API-запросам.
- Сохраняется локальная сеть Content Hub → Image Production и обязательный `compose.integration.yaml` при пересоздании web.
- Проверены реальная TLS-цепочка, мобильный share, превью ссылки, целевой трафик и восстановление из внешнего backup.
- Для Docker-реализации выполняются проектные проверки диска/контейнеров до и после; текущая консультация контейнеров не создаёт.

Измеряем полезность пилота: сколько создателей публикует работу повторно, сколько внешних посетителей переходит в продукт, сколько обращений получают авторы, какова доля жалоб и ручная стоимость модерации. Численные целевые значения задаются до пилота после определения его аудитории; сейчас спрос и конверсия не подтверждены.

## 14. Что нужно уточнить перед выкладкой

1. Подтвердить финальный корневой домен и допустимость переноса нынешней Studio на `studio`.
2. Снять фактическую конфигурацию сервера: процессы, edge, RAM/CPU, диски, storage, backup и текущие версии приложений. Проверить источник TLS-ошибки.
3. Проверить существующие production-пользователи, привязки Workspace и consumers; подготовить их сохранение/сопоставление.
4. Выбрать первый формат челленджа, модератора и стартовые разрешённые работы/уроки для непустого запуска.

Эти пункты не препятствуют консультации и разработке публичных страниц, но нужны для безопасной миграции и запуска community на реальных данных.
