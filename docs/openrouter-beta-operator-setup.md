# OpenRouter и Telegram: подготовка оператором бета-пилота

Дата: 19 сентября 2026. Модуль управляемых бюджетов реализован и проверен на тестовых данных. Реальные секреты, подключение бота и включение на сервере выполняются отдельным согласованным шагом.

[Актуальный план](/Users/m.pyzhov/WORKSPACEs/Development/PRODaction/image-prodaction/Repos/image-prodaction/docs/production-pilot-plan-2026-09-19.md).

## 1. Что выпустить в OpenRouter

1. Войти в тот OpenRouter аккаунт, на котором будет общий запас средств участников.
2. Открыть [Management API Keys](https://openrouter.ai/settings/management-keys).
3. Нажать Create New Key.
4. Назвать, например, REVERIE beta provisioning.
5. Задать срок действия с запасом на пилот; перед истечением понадобится замена.
6. Сразу сохранить показанный секрет в менеджере паролей/секретов. Повторно посмотреть его не получится.

Нужен один **Management API key**, а не вручную выпущенный ключ для каждого участника. Generation keys сервер будет создавать самостоятельно. Management key не используется для генерации или Ask AI.

Процедура и назначение подтверждены [официальной документацией](https://openrouter.ai/docs/guides/overview/auth/management-api-keys).

## 2. Куда передать секрет

Имя серверного секрета: `OPENROUTER_MANAGEMENT_API_KEY`. Его читает платформенный модуль бюджетов в Identity; IP не получает этот ключ.

После подготовки сервера его значение нужно добавить через защищённый интерфейс secrets инфраструктуры. Альтернатива — файл вне репозитория, доступный только сервисному пользователю; точный путь и механизм инъекции определяются при настройке сервера. На этапе подготовки достаточно сохранить ключ в менеджере секретов и сообщить, что он готов и где хранится, без самого значения.

Не помещать значение в этот чат, Telegram, Git, frontend-переменные NEXT_PUBLIC_*, shell argv или общедоступные логи. Обычные IP web/worker не должны получать Management secret: он нужен только модулю управления бюджетами и мониторингу общего запаса.

Ключи участников шифруются на сервере и привязываются к личному Workspace. В UI доступен статус/остаток, не plaintext ключ.

## 3. Общий запас средств

Открыть [OpenRouter Credits](https://openrouter.ai/credits) и пополнить общий аккаунт вручную. Само создание ключей и выставление лимита деньги на аккаунт не добавляет.

Рекомендуемый режим пилота — контролируемый общий запас, без автоматического пополнения карты. Автопополнение можно включить отдельно, если владелец примет такой режим. Проверьте текущую комиссию, валюту и итоговый размер зачисления в интерфейсе перед оплатой; эта инструкция не задаёт тариф.

Для каждого пользователя модуль будет использовать фиксированный накопительный лимит без reset. Пример: потрачено $6 из лимита $10, начислено ещё $5 → новый лимит $15, остаток около $9.

Бюджеты всех участников используют один запас OpenRouter, поэтому сумма обещанных доступных бюджетов должна быть обеспечена средствами с выбранным резервом. Небольшое превышение индивидуального лимита возможно при параллельных запросах; дополнительно вводятся серверные ограничения.

Источник: [ключ на клиента и общий пул](https://openrouter.zendesk.com/hc/en-us/articles/51680687417499-Can-I-create-one-API-key-per-user-with-its-own-spending-limit-Management-API-keys).

## 4. Что подготовить для Telegram

- Платформенный бот, созданный/выбранный через официальный [BotFather](https://t.me/BotFather).
- Username бота.
- Bot token в защищённом хранилище: он понадобится для исходящих уведомлений и работы с файлами.
- Webhook secret и будущий HTTPS URL.
- Числовой Telegram user ID владельца для закрытых операторских команд. Username не используется для назначения прав.
- Владелец должен открыть бота и отправить /start, чтобы бот мог доставлять ему личные сообщения.

Не переназначать webhook уже используемого Content Hub бота без проверки его роли. У одного бота один webhook ingress; вход и операторские команды маршрутизируются на сервере. Сам факт первого /start не назначает админом: ID сверяется и вносится в защищённую конфигурацию при настройке.

Identity использует `IDENTITY_TELEGRAM_BOT_USERNAME`, `IDENTITY_TELEGRAM_WEBHOOK_SECRET`, `IDENTITY_TELEGRAM_BOT_TOKEN` и `PLATFORM_ADMIN_TELEGRAM_ID`. Владелец разрешил использовать существующий тестовый бот Content Hub/Reverie; VPN-бот исключён.

## 5. Что согласовать перед первым пополнением

1. Желаемый пилот уточнён владельцем: внешний банковский перевод, чек в бота, ручная проверка поступления и подтверждение начисления. Stars и платёжный шлюз сейчас не подключаются. Отдельно уточнить применимость правил Telegram к конкретному пути пользователя.
2. Валюта/сумма поступления и какой AI-бюджет получает участник.
3. Курс для конкретной операции. Пример владельца — 5000 ₽ при 100 ₽/$ дают $50; постоянный курс этим не установлен.
4. Нужен ли срок использования бюджета. Если нет принятого правила, дату окончания не показываем.
5. Warning и critical thresholds общего OpenRouter остатка.
6. Модели и допустимая параллельность пилота.

Для продажи цифровых услуг внутри Telegram требуется Stars; отсутствие Payments API само по себе не создаёт исключения. Получение файла чека ботом поддержки отдельно не запрещено найденными положениями, но схема продажи с реквизитами и начислением в боте может подпадать под общее правило. Последнее — оценка применимости, а не прямой ответ Telegram именно про ручные чеки. [Telegram Payments FAQ](https://core.telegram.org/bots/payments-stars#q-i-run-my-own-website-to-process-sales-does-this-mean-i-dont-have-to-use-telegram-stars), [Developer Terms 6.2](https://telegram.org/tos/bot-developers#62-digital-goods-and-services).

## 6. Как будет выглядеть работа оператора

Карточка заявки содержит идентификаторы получателя и заявки, сумму начисления USD и пояснение оператора о переводе/курсе. Личный Workspace определяется сервером при подключении ключа после первого входа пользователя в IP.

Оператор проверяет поступление денег и нажимает «Подтвердить и начислить $50». Изменение суммы сначала обновляет карточку подтверждения. Повторный клик не создаёт второго начисления.

Модуль:

- находит аккаунт по проверенной Identity-связи;
- создаёт/обновляет OpenRouter key;
- шифрует/подключает его;
- перечитывает результат;
- отправляет уведомление только после успешного применения.

Если процесс прервался после подтверждения, виден статус «Начисление обрабатывается» или «Нужна проверка». Повторяются технические шаги, а не денежная операция.

## 7. Оповещения владельца

Проверка общего баланса — каждые 5 минут, дополнительно после применения начисления и по команде оператора. При смене уровня сообщение приходит только владельцу; для critical или недоступной проверки без подтверждения — напоминание через 10 минут. После восстановления — одно сообщение.

Пример:

> OpenRouter: общий запас ниже порога.
> Доступно: $24.70
> Проверено: 14:05
> Порог: $30.00
> Проверить сейчас · Увидел · Открыть Credits

Порог $30 и остаток здесь иллюстративны. Значения будут настройками. Сбой получения баланса не показывается как нулевой остаток. Предусматриваются повтор доставки и контроль давности успешной проверки.

## 8. Проверка подключения

Сначала выполнить read-only проверку Management API и общего остатка без вывода секрета. Создание/отзыв служебного тестового ключа и контрольное начисление выполнять как явно обозначенную приёмку, не смешивая с реальными клиентскими деньгами.

До запуска подтвердить:

- Management key читается только нужным модулем;
- новый пользователь получает свой credential, без доступа к чужому;
- Ask AI и генерация используют один пользовательский key;
- повтор подтверждения не меняет бюджет второй раз;
- отклонённая заявка ничего не начисляет;
- сбой OpenRouter не вызывает ложное уведомление об успехе;
- низкий общий остаток и сбой проверки видны только оператору;
- Telegram-only Identity работает без SMTP.

## Реализованный контракт пилота

Модуль находится в репозитории платформы: `apps/identity/src/budgets`.
Секреты и реальное включение владелец вынес в отдельный следующий шаг.

- `PLATFORM_BUDGETS_ENABLED=true` включает модуль только при полном наборе настроек.
- `OPENROUTER_MANAGEMENT_API_KEY` — Management key, `IDENTITY_TELEGRAM_BOT_TOKEN` — токен тестового платформенного бота.
- `PLATFORM_ADMIN_TELEGRAM_ID` — единственный оператор.
- `PLATFORM_BUDGET_KEY` — отдельный ключ шифрования (32 байта base64), хранить с бэкапами.
- `PLATFORM_PROJECTION_SECRET` — общий секрет подписанных запросов Identity → IP, минимум 32 символа.
- `PLATFORM_IMAGE_PRODUCTION_URL` — адрес IP, `PLATFORM_BALANCE_WARNING_USD` и `PLATFORM_BALANCE_CRITICAL_USD` — пороги.

Команды оператора: `/credit <UUID заявки> <USD> <сумма/валюта/курс/основание>`, затем кнопка подтверждения; `/reject <UUID>`, `/retry <UUID>`, `/budget_status`, `/balance`.

Суммы записываются в целых центах. PostgreSQL запрещает изменять/удалять строки журнала начислений. Неопределённый результат выпуска/изменения ключа переводит аккаунт на проверку. Для потерянного нулевого ключа предусмотрена отдельная команда восстановления с проверкой OpenRouter и отключением нулевых дубликатов.

IP принимает только подписанный `POST /v1/platform/budget-connection`: проверяет срок подписи, issuer и `issuer#subject`, находит существующий аккаунт и его личный Workspace. Если пользователь ещё не открыл IP, начисление остаётся подтверждённым и ждёт первого входа. Повтор доставки не создаёт новую учётную запись или второе начисление.

`PLATFORM_PAID_REQUEST_GUARD=true` ограничивает параллельное исполнение по одному ключу между web и worker. Для видео удерживается ограничение на время ожидания результата. После аварии процесса внешняя операция может продолжаться; это не обещание абсолютно точного финансового резервирования. Ключи пользователям не выдаются в интерфейсе.

Подробный порядок настройки и восстановления: `docs/identity-pilot-operations.md` в репозитории Content Hub/платформы. Помощник безопасного ввода: `scripts/identity-pilot-config.mjs`; он скрывает ввод, создаёт новый файл 0600 и ничего не деплоит.
